# Subsystem Boundaries

`ImageViewport` separates Qt item adaptation, canonical viewport state transitions, provider transport, frame preparation, render synchronization, playback scheduling, and scene graph presentation. The engine is the sole owner of canonical viewport state; surrounding responsibilities perform work and return correlated outcomes without becoming alternate state authorities. These responsibility names do not require separate classes, ports, node counts, or a fixed internal graph, and an implementation may combine or split them while preserving ownership and dependency direction.

## Dependency Direction

Canonical state authority depends on domain values and bounded capabilities, not on the component item, provider implementations, timers, scene graph objects, or backend resources. Provider, rendering, scheduling, and item adaptation cannot coordinate around that authority or mutate one another's state; facts that affect viewport behavior return to the canonical owner for an atomic decision. Shared contracts remain acyclic and contain no mutable subsystem ownership.

## Caller Policy Boundary

KiriView owns source discovery, navigation scope, page pairing, fallback policy, application source identity, route-transition meaning, action availability, decoder and cache choices, display-store lifetime, predecode and refinement payload production policy, credentials, sandbox policy, gesture interpretation, stepped reading movement, and nearest-point or snapping policy before they become viewport commands. The viewport accepts only `ImageSequence` handles through typed presentation-target values.

KiriView must enforce application ownership and authorization before invoking the component. The item applies the same value validation and state-transition contract to every declared C++ and QML entry point and must not be treated as an application-owner authorization boundary.

The caller expresses transition intent through `PresentationTargetTransitionPolicy`, but the engine owns fit, zoom, content position, rotation, mirroring, spread direction, page gap, visible geometry, coordinate conversion, status, playback phase, diagnostics, and revisions. Caller policy must not repair a partially applied target transition through ordered follow-up mutations.

## Item Boundary

The component item owns command entry points, component property and signal adaptation, item/window geometry capture, and conversion between declared Qt values and canonical inputs. Production QML registration remains application-owned as defined by [Repository Component Boundary](component-boundary.md). The item publishes only complete canonical snapshots and must not maintain independent mutable projections of request, display, presentation, or role state.

The item connects accepted state with provider, render, geometry, and scheduling work while preserving atomic public publication and the documented effect semantics. Synchronous callbacks and inputs arriving from other threads are serialized before they affect canonical state, so callers never observe a partially applied transition and an older transition cannot overwrite state or scheduling derived from a newer one. The internal call and notification choreography is not an architecture contract.

The item does not interpret provider events, allocate request or revision identities, match stale results, decide render readiness, own playback phase, or retain scene graph resources.

## Engine Boundary

The engine owns accepted presentation-target identity, per-role request ordering and correlation, provider and demand correlation, payload and render admission, status and diagnostics, independent per-role playback, restorable and discardable retained presentation, preferred and effective zoom, canonical presentation state, and component revisions. These domains remain one canonical authority; their internal partition and representation are not architecture contracts, and no collaborator may mutate them outside that owner.

Each accepted command or runtime fact affects canonical state atomically or leaves it unchanged. Public value shape is validated before capability, failure-scope, or generation-state checks. Rejected commands may affect only command diagnostics as permitted by the public command contract, and coordinate helper validation is a read-only geometry operation that cannot affect command state. No particular reducer, command port, or effect representation is required.

Async work begins only after its owning generation, request, demand, payload, or render lifecycle is accepted into canonical state. Results carry enough owner-issued correlation for stale or retired outcomes to be rejected before they affect state, diagnostics, revisions, playback, or visible content. Cancellation and cleanup are idempotent, and owner-side retirement never waits for provider or render cleanup.

Presentation-target replacement is an atomic cross-domain transaction. It validates the complete role set and policy, establishes the new target identity, derives target presentation state or retains unresolved target-scoped geometry intent, selects retained or empty display, establishes initial role work, and applies the documented playback transition. `RestorePrevious` additionally retains the complete prior committed state and resources needed to restore its accepted request, presentation, display, provider ownership, and per-role playback without new source work; how that state is represented is not an architecture contract. A clear target admits only the canonical clear policy, removes retained ownership, and leaves presentation preferences unchanged. Caller-declared same-target refinement requires the compatible metadata, logical size, role set, timing, and authored-animation facts defined by the public contract and establishes its requests within the new accepted generation; provider-supplied refinement remains within an existing generation.

A target spread reaches ready request ownership only when every required role has an authoritative payload for the active identities validated and render-committed. Before that point, the engine may publish a complete active spread containing admitted provisional pixels while keeping request state loading; it preserves authority stage through preparation and rendering, never publishes a partial spread, and never retires the provider token merely because provisional pixels committed. Failure scope, aggregate severity, role precedence, and diagnostic selection follow [ImageViewport](../spec/image-viewport.md#page-roles-and-spread-presentation) and [ImageViewport State](../spec/image-viewport-state.md#snapshot-values). Required sibling work remains eligible while its outcome can change the prescribed aggregate status, reason, or winning diagnostic, and sibling success never publishes a partial spread. A terminal replacement under `RestorePrevious` records a `RestoredTransition` failure observation, retires the failed generation, and atomically restores the pinned commit before snapshot publication. Later requests recover only from the display-request-terminal scope allowed by the public contract, while generation-terminal state requires clear or target replacement. Transport availability cannot independently authorize recovery. Presentation changes and demand bookkeeping reuse committed authoritative payload ownership and do not reset ready request status; provisional display and unsatisfied current-detail demand remain separately observable, and ordinary auxiliary-refinement failure cannot overwrite ready request state or display-request-terminal diagnostics.

Retained display is a separate authoritative ownership domain. It carries the displayed generation and presentation identity that produced its pixels and cannot satisfy the newer target's readiness, capabilities, playback, or commands. Provisional pixels are active loading presentation only and cannot become retained or restorable ownership. Discardable fallback under `KeepFailedTarget` may release payloads for resource pressure and publish empty placeholder display without changing the accepted request or presentation state. A commit pinned for restoration is not visual-only fallback: every part needed for restoration remains owned until the replacement commits or terminally restores, and resource admission must fail the replacement rather than dismantle that state.

## Snapshot Boundary

Snapshot projection is an engine responsibility. `ImageViewportStateSnapshot` groups request, display, presentation, per-role observations, diagnostics, and revisions into one immutable coherent value. Projection follows the canonical schema and valid status/phase combinations in [ImageViewport State](../spec/image-viewport-state.md); unavailable observations use the specified invalid values.

Request, display, canonical-presentation, target-presentation projection, displayed-presentation projection, command, snapshot, and per-role demand revisions have separate ownership. Canonical-presentation identity follows every component presentation field; target and displayed projection identities follow only inputs that affect the accepted or displayed render/geometry projection. A token advances only when a field or projection in its domain changes. Snapshot publication and `stateChanged` follow complete snapshot changes, while an accepted no-op preserves every revision and emits no notification. Tokens remain opaque and equality-only at component boundaries.

The engine allocates valid request, display, presentation, command, and snapshot revision identities before publishing the initial snapshot. Each role request snapshot projects its own playback phase, and aggregate terminal request state retires every role's playback before snapshot publication.

Coordinate helpers consume the same displayed-geometry projection as rendering and role geometry. They must use the retained displayed presentation identity when retained pixels are visible and must never combine it with the newer target presentation.

## Sequence Boundary

`ImageSequence` is an opaque content handle for validated in-memory or provider-backed image data. Factories own construction-time validation for still frames, timed frame entries and intervals, provider descriptors, authored animation facts, and public source limits and return the canonical typed factory result without partially constructed handles. In-memory construction stores immutable frame, timing, seek, and animation facts; provider construction stores authoritative descriptor facts and session-creation capability. Neither performs a viewport request, provider source access, session creation, render work, scene graph work, or application navigation.

Provider-backed handles may be used concurrently. Each role within an accepted presentation-target generation receives an independent provider session; failure to create one is scoped to that generation and role and enters the engine as provider failure.

## Provider Boundary

The provider boundary owns session storage, request and event delivery, threading-contract enforcement, best-effort cancellation and close delivery, transferred frame-handle and application failure-handle release delivery, and affinity-correct destruction. Its event-ingress and cleanup ownership outlives any revocable item callback until transferred handles and closing sessions converge. It receives accepted provider work and returns normalized events and host-failure causes, including command-delivery failure for response-bearing commands; the internal transport representation is not an architecture contract. Provider-authored free-form diagnostic text does not cross this boundary. An admitted provider failure may carry a typed generic cause plus an opaque application failure handle; the boundary validates its shape but never resolves or renders the reference. The canonical owner retains the admitted handle until its failure observation becomes unreachable, and the provider boundary delivers exact-once release on the specified affinity. The provider boundary does not own token admission, request queues, terminal scope, command recovery, component failure projection, diagnostics, playback, rendering, or notifications.

Each provider session has one serialized command stream. Provider events may originate from worker facilities, but the provider boundary normalizes their delivery before canonical admission. Frame, position, and playback requests carry viewport-authored demand; providers may select complete-frame detail but cannot own or infer viewport geometry, target identity, or render state.

## Preparation And Render Boundaries

Frame preparation validates and normalizes complete CPU-backed payloads into the source logical page-space contract before render ownership while preserving whether provider delivery was provisional or authoritative. It establishes the complete-frame payload raster and logical-to-raster mapping facts from the normalized image and authoritative source logical size. Source logical geometry and payload resources are separate authorities: logical metadata establishes page identity without causing proportional allocation, while payload raster, retained bytes, backend texture size, per-demand byte cap, and display budget constrain actual resource ownership. The full source logical area edges and full payload raster edges are corresponding boundaries; representational roundoff at those boundaries is not a render failure, while materially out-of-bounds source or raster areas are rejected without changing the public half-open point-containment contract. Preparation must enforce metadata consistency, timing identity, orientation, exactness, source-to-payload mapping, authority-stage eligibility, and every applicable logical and payload limit with overflow-safe calculations before allocation-dependent copying or rendering for both in-memory and provider-backed sources. A well-formed authoritative inexact payload under `RequireExact` returns unsupported payload rejection; an ineligible provisional candidate is released without retiring the authoritative request. Malformed or inconsistent authoritative payload facts return error payload rejection. Preparation returns a coherent admitted payload or structured failure and does not publish readiness.

The rendering boundary owns Qt Quick synchronization, backend resource handoff, and scene graph lifetime. It receives one coherent complete-spread render attempt and returns a correlated commit or failure outcome. It must not inspect provider sessions, reconstruct canonical geometry, choose request status, run playback timers, or publish public observations; the exact internal input and callback representation is not an architecture contract.

## Playback Scheduler Boundary

The scheduling boundary owns timer resources, monotonic elapsed-time capture, and timeout delivery. Every elapsed interval remains correlated with its role, generation, and schedule lifecycle before canonical admission. The engine alone owns each role's phase, target selection, loop policy, catch-up suppression, provider request identity, and stop/pause ordering. Physical wakeup coalescing cannot merge role clocks or remove role identity, and the internal timer-notification representation is not an architecture contract.

## Trust, Diagnostics, And Observability

All caller and provider values are untrusted at their admission boundary. Shape, enum, finite-number, size, timing, byte, token, role, generation, demand, failure-cause, failure-handle, and failure-reference checks must occur before the value can influence allocation, rendering, or canonical state. Arithmetic used for dimensions, durations, and byte bounds must be overflow-safe. Payload content, caller credentials, and provider-authored free-form text must not enter component diagnostics. A valid opaque failure reference is correlation data only and cannot affect engine branching, allocation, rendering, or diagnostic text; malformed, rejected, and stale handles still enter exact-once release.

Component diagnostics are viewport-authored from typed failure categories and trusted internal validation results and follow the ownership and clearing rules in the state specification. The diagnostic value boundary applies plain-text normalization and Unicode-scalar truncation before publication, and engine decisions never branch on diagnostic strings. Internal observability records structured subsystem, role, generation, request, demand, payload, render-attempt, and failure-reference presence with failure categories sufficient to attribute stale drops, admission failures, cleanup, and backend failures; it must not change component outcomes or expose image content, credentials, raw provider diagnostics, application failure contents, opaque reference representations, or backend object addresses.
