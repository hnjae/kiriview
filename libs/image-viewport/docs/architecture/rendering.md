# Rendering

Rendering translates prepared complete-frame CPU payloads and engine-owned presentation projections into encapsulated Qt Quick updates. Backend choice and resource lifetime remain behind the render host. Native texture injection, tiled or partial payloads, caller-owned scene graph resources, and caller-owned Qt Quick image items must not enter payload admission or request state.

Presentation geometry is owned by the engine and specified in [Presentation Geometry](presentation-geometry.md). Rendering consumes the engine-authorized geometry projection and must not reconstruct canonical fit, zoom, pan, spread, rotation, mirror, visible-rectangle, or coordinate-conversion state from render-local resources.

## Render Data Flow

Prepared payloads carry immutable logical-page, raster, sampling, alpha, timing, orientation, role, quality, exactness, payload, and authority-stage identities. Preparation normalizes orientation and fixes the complete-frame raster and logical-to-raster mapping facts from the normalized image and authoritative source logical size before render admission; render code must not infer public geometry from raster size or `QImage::devicePixelRatio()`. The full source logical area edges correspond to the full payload raster edges. Render adaptation treats representational roundoff at corresponding area boundaries as the same boundary rather than a render failure, while materially out-of-bounds source or raster areas fail validation. This area-boundary rule does not relax the public half-open point-containment contract. Lower-detail and refinement rasters may differ while preserving that contract. Color metadata may affect internal rendering but must not change public geometry, status, coordinate conversion, identity, or ordering.

Each render attempt receives one coherent immutable input containing the complete ordered role set, payload identity and data, geometry projection, backing fields, and relevant quality preferences. Rendering may adapt that input to backend values but must not query live sequences, providers, requested or displayed state, or mutable payload storage to assemble or repair the layer set. The internal input type is not an architecture contract.

The rendering boundary creates or updates scene graph resources only on the appropriate Qt Quick synchronization or render path. GUI-side cleanup invalidates rendering references without dereferencing raw scene graph pointers after ownership has moved to the render side.

The rendering boundary validates attempt completeness without scene graph allocation before materializing backend resources. Backend allocation runs only on the valid Qt Quick synchronization or render path and reports a correlated commit or failure for the immutable attempt.

Frame handles remain provider-visible lifetime boundaries even after rendering ownership moves into the viewport. The viewport may retain a handle while its payload is visible, retained as authoritative fallback, pinned for restoration, or pending render commit; it releases the handle exactly once when no component, retained-display, or restoration state can reference that payload. Provisional payloads cannot enter fallback or restoration ownership. Memory pressure may discard only authoritative fallback owned by `KeepFailedTarget`. Render failure releases the failed candidate payload unless it already belongs to the pinned prior commit.

Retained fallback display keeps the request target and presentation snapshot that produced its pixels and geometry. New accepted request or presentation state may advance while retained pixels remain visible, but displayed geometry, coordinate helpers, and render synchronization for those retained pixels continue to use the retained identities until the active target and presentation commit or retained display is cleared. Retained and accepted target generations may match when fallback precedes the active frame, position, or presentation identity. A commit pinned for `RestorePrevious` additionally retains the prior accepted request state, provider sessions, complete role payload set, and per-role playback state needed to promote that commit back to active ownership without source work; its internal storage shape is not an architecture contract.

Payload, authority stage, target-spread, presentation, and render-attempt identities are independent. Payload changes require a new prepared identity and correlated commit outcome. A two-page target requires one outcome covering the complete required role set before any active display ownership is first published; role failure must not expose a partial spread. A complete spread containing provisional pixels may become active visible display while its authoritative request remains loading. Later authoritative role results combine with matching siblings and replace provisional detail atomically; readiness is published only after every required role is authoritative. Presentation-only and demand-only changes reuse committed authoritative payload ownership and do not reset ready request status. An auxiliary refinement changes only the matching role within the complete committed role set, so commit replaces display detail atomically and failure leaves the previous spread intact. A prepared payload becomes public display content only after the canonical owner accepts the matching commit.

A render outcome is admissible only when its target spread and every required role payload identity match the active attempt. Failure correlation identifies the affected required role, so stale or non-required outcomes are discarded without changing newer request or display state. The callback and acknowledgement representation is not an architecture contract.

Commit authority is serialized per target-presentation identity while provider and preparation work for different roles may complete concurrently. Only the newest accepted complete role set may commit; an outcome for a superseded candidate or presentation is stale. A sibling refinement commit must not discard another role's still-current prepared work or reintroduce an older payload identity. Candidate retention, coalescing, and retry construction are implementation choices.

Render failure outcomes carry a structured internal cause for operational attribution. Rendering must not choose public status or transition behavior; the canonical owner admits only an outcome matching the active attempt and applies the provisional, terminal, restoration, and auxiliary-refinement guarantees in [ImageViewport](../spec/image-viewport.md#requests-commands-and-playback) and [ImageViewport State](../spec/image-viewport-state.md#display-phase-invariants). Failure to render a provisional candidate drops that candidate while preserving its authoritative provider request; failure to render a required authoritative target or auxiliary candidate follows its documented terminal or preservation scope. Candidate ownership is released or retained according to that admitted outcome, and stale failures cannot affect newer request or display state.

Scene graph invalidation discards backend resources, not canonical payload or display identity. Rendering rebuilds from the latest coherent attempt input when synchronization becomes available. Absence of a usable window or positive item geometry keeps new work render-waiting; it is not itself a render failure. A genuine rebuild failure for the active attempt follows the normal render-failure path.

## Quality Requests

The rendering boundary consumes canonical smoothing and mipmap preferences and reports a fallback fact when the active backend cannot honor them. The canonical state owner controls the resulting warning lifetime and display revision and must not convert an optional rendering fallback into payload rejection or request failure.

## Background

Transparent, solid color, and checkerboard backgrounds are item backing presentation. Solid color consumes `backgroundColor`; checkerboard consumes its stored light color, dark color, and positive item-logical cell size and remains axis-aligned to item space. Background fills local item bounds behind image content and does not contribute to content geometry, image coordinate validity, or request readiness.

Background rendering is independent of payload admission. A background-only update must not advance request status, display frame, displayed position, or playback phase.

An accepted presentation change advances the display revision when it changes a visible display observation, even when committed payload identities are unchanged. A complete no-op advances no revision.
