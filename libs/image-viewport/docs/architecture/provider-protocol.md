# Provider Protocol

Provider integration adapts application-owned page sources into the same sequence and request model used by built-in frame lists. Providers own source-specific production behind the adapter boundary; the viewport engine owns request identity, token matching, stale-result filtering, display-demand projection, status projection, diagnostics, playback ordering, retained display, and render readiness.

The component owns the provider diagnostic category and exposes its actual category object across the supported host boundary. Host diagnostic modes enable that object rather than owning or duplicating the component's logging identity.

## Descriptor And Sessions

Provider-backed sequence construction captures an `ImageSequenceProviderDescriptor` containing construction metadata, threading contract, and a stored session factory. Every available construction-metadata field is authoritative, and unknown facts use explicit unavailable values. Descriptor construction and storage are side-effect-free; expensive source work starts only when the provider boundary invokes the factory for a role within an accepted presentation-target generation.

A provider-backed sequence creates an independent session for each role within an accepted presentation-target generation, including concurrent uses of the same `ImageSequence` handle. Construction validates only descriptor facts available without invoking the factory. The immutable factory may be invoked concurrently from different viewport command-processing threads; the descriptor owns the callable lifetime, while synchronization of provider state captured by that callable remains a provider responsibility. The generation and role are accepted before invocation, and a failed or malformed result, including an invalid failure cause, malformed application failure handle, or session object already owned by another live lifecycle, becomes provider failure for that generation and role alone. Any failure handle transferred by a rejected factory result is released exactly once.

Provider transport may create, command, cancel, close, and clean up sessions, but session identity, accepted-generation matching, token allocation, queued-work policy, cleanup interest, and retirement are engine-owned.

## Requests

Provider sessions receive the canonical request values defined by the component provider protocol. Metadata, frame, position, and playback requests carry engine-allocated opaque tokens; frame, position, and playback requests also carry engine-authored display demand for the target role. Cancel requests identify provider work whose engine tokens have been retired or marked for retirement; they do not control engine progress. Close requests are best-effort cleanup after engine-side generation retirement and have no event contract.

Frame requests target a resolved frame. Position requests preserve the public requested position and carry the resolved frame identity needed for payload validation. Playback requests carry playback-origin token identity and may produce frame readiness or end-of-sequence events. Unknown-target initial assignment requests metadata first and sends no frame, position, or playback request until metadata selects a valid target.

Display demand is a value snapshot, not provider-owned viewport state. Its public fields are defined by `ImageSequenceProviderDisplayDemand` in [ImageSequence Provider Protocol](../spec/image-sequence-provider-protocol.md#provider-demand-and-payload-values). Demand lets providers choose complete-frame preview, exact, bounded-detail, cached, or refinement payloads without receiving scene graph resources or QML image-provider state. Exactness preference is an admission constraint: `RequireExact` classifies a newly offered well-formed authoritative inexact payload as unsupported payload rejection even when the demand revision matches, while an inexact provisional candidate is released and ignored without retiring the authoritative request. An event for a retired token or demand is stale and is released and ignored; an authoritative envelope that fails to echo the demand recorded for its still-active token is an active error payload rejection scoped to the owning display work or auxiliary refinement. Visible detail must have been admitted under the demand active at its commit, and cached payload reuse must be resubmitted under the current token and demand revision.

Payload resource admission is one coherent target-spread decision that accounts for every required role and retained payload ownership, so concurrent provider completions cannot oversubscribe the display budget. A cap or allocation-accounting change advances allocation generation and demand revision for affected work; it cannot silently reinterpret an already issued demand. The internal reservation and accounting representation is not an architecture contract.

Component opaque identity types preserve their engine ownership domains. Presentation-target generation identifies accepted or displayed target ownership, allocation generation identifies payload-budget and accounting state, demand revision identifies payload admission, and state revision identifies a component observation domain. These identities are not substitutable or cross-comparable even when their internal allocators happen to produce equal representations.

Each session receives serialized commands and events are serialized before they affect canonical state. Event ingress is a synchronous conditional-ownership boundary that does not wait for canonical event handling or downstream delivery capacity: accepted non-advisory events retain FIFO order and transfer any handle, while rejection or closure leaves ownership with the provider. Admission preserves session, request-kind, role, generation, demand, cancellation, terminality, and transferred-ownership facts so it never depends on callback order, delivery timing, provider affinity, or provider object identity. An eligible provisional offer followed synchronously by its valid terminal offer is accepted in order without awaiting canonical handling between them. A timed-metadata value retains only a bounded over-limit representative, and ingress rejects that representative before retiring the matching active metadata-request token so corrected metadata can still answer the same request; stale, mismatched, and wrong-kind offers keep their ordinary protocol classification. Other bounded metadata violations admitted for canonical validation remain generation-terminal. Across all provider affinities, accepted-but-unhandled work and transferred ownership remain bounded, excess malformed, stale, duplicate, or mismatched offers are rejected before ownership transfer, and accepted non-advisory ownership remains outstanding until canonical state handles the event or it definitively becomes undeliverable. Advisory work may be coalesced, omitted, or overtaken by terminal processing but remains bounded. No particular admission, accounting, or serialization representation is required.

## Events

Provider sessions report the canonical event values defined by the component provider protocol. Events for metadata, frame, position, and playback work echo the token of the original request they answer. `Cancelled` events echo the original token being cancelled; `Close` has no event contract.

The engine validates session identity, generation identity, token scope, request/event kind compatibility, page role, active request identity, cancellation state, provisional stage, and terminality before an event can mutate state. An eligible ordinary still-image token accepts at most one non-terminal provisional frame and every response-bearing token accepts at most one terminal event. Admitting provisional pixels preserves the token, authoritative request, and terminal obligation; an ineligible provisional candidate is released without converting that candidate into authoritative request failure. Late or duplicate events for stale, cancelled, terminal, or closed work are released and ignored without changing component state, display content, playback phase, diagnostics, or revisions. A token, kind, session, or role mismatch for still-active work is a protocol violation; a syntactically compatible terminal frame-ready event proceeds to payload admission, where demand, frame, and timing mismatches are payload rejection with display-request-terminal or auxiliary-only scope according to the owning work.

Unsupported events carry an explicit cause: `UnsupportedRequest` or `PayloadRejection`.

Failed events carry one valid generic provider cause and an optional opaque application failure handle. Admission validates only value shape, the cause, and handle reference well-formedness. The canonical owner retains an admitted handle with the winning terminal fact and exposes only its reference for snapshot correlation; it never resolves the reference, branches on its identity, converts it to text, or records its representation. Provider-authored free-form diagnostics are not accepted. KiriView's provider owner remains responsible for the referenced typed failure value, while the handle release callback is the sole authority for retiring its lookup record.

Waiting and progress events are advisory. They may update request wait projection for the active token, may be coalesced, and must never dominate terminal results for the active token. A provisional frame is likewise non-terminal but may supply display pixels under the active target identity while request projection remains provider-waiting.

## Terminal Ownership

Generation-terminal and display-request-terminal facts remain independent semantic scopes associated with the affected generation, role, and, for display work, request identity. Provider-originated facts retain their admitted generic cause and optional application failure handle. A new accepted display request retires only the matching display-request terminal and cannot erase or bypass a generation terminal. Clear and non-restoring non-empty target replacement retire both scopes for that generation. `RestorePrevious` retains the winning replacement failure as a `RestoredTransition` observation while restoring the prior generation. Aggregate projection applies the deterministic role and severity precedence from the public contract; the internal storage shape is not an architecture contract.

Provider session availability is transport execution state, not a second authority for command recovery. Session-open failure, active protocol violation, failure to deliver any response-bearing command, and provider request-token exhaustion record a generation terminal before converging on generation close. No same-generation request may reopen, replace, or retry that session. A queued-frame scheduling failure occurs before provider delivery, records only a display-request terminal, and leaves the accepted session available for a later request.

## Metadata

Metadata readiness is generation-scoped. Runtime metadata supplies frame count, sequence-wide source logical size, timing model, seek support, timed playback support, authored animation facts, and timing intervals. It becomes authoritative only after validation against public limits and construction-time constraints. Source logical size establishes geometry and identity only; accepting it must not allocate a raster, byte buffer, texture, or other storage proportional to logical dimensions.

The engine may project each validated authoritative construction-time fact while other metadata fields remain explicitly unavailable. This partial projection must not select an unknown initial target or relax later runtime validation; target resolution waits for the complete metadata required by the selected still or timed model.

Complete construction-time metadata may select initial frame `0` during assignment. Unknown or partial construction-time metadata leaves the initial target unknown until validated runtime metadata creates a metadata-bound display request for the still-active initial request.

Validated metadata may complete generation facts after the active display request has changed when session and generation identities still match and the generation has not closed. It may bind only a still-active unknown target and must not revive stale initial, seek, playback, clear, or replacement requests.

Except for an active timed collection rejected at ingress because its count exceeds the public envelope, malformed metadata, contradiction of construction-time facts, non-contiguous timing, non-positive durations, invalid dimensions, provider protocol violation, and admitted public-limit violation are generation-terminal payload-rejection errors. Accurate metadata proving unsupported sequence content is generation-terminal unsupported state. Unsupported operations for otherwise valid content are scoped to the active operation that required them.

## Payload Admission

Frame-bearing events transfer a handle owning one `ImageFrame` plus an `ImageSequenceProviderFrameEnvelope` and preserve whether the event is provisional or authoritative through preparation and render admission. The preparation boundary validates reusable payload facts from the frame, request-scoped demand and timing identity from the envelope, their consistency with validated metadata and the active request, and all public and effective runtime limits before render ownership begins. Logical-dimension admission and payload-resource admission are independent checks, and every dimension, scale, pixel-count, and byte calculation is validated for overflow before allocation-dependent ownership or copying.

The frame's source logical size must match validated sequence metadata for that role. Its payload raster may differ from source logical size, but it must be finite, positive, and complete-frame after orientation normalization, with the full logical and raster axes mapped as defined by the public payload contract. Public raster dimensions and payload bytes are unconditional ceilings; backend texture size, per-demand payload bytes, and display byte budget are independently tighter runtime ceilings when valid. None constrains source logical dimensions. The envelope's demand revision must match the answered request, and its timed frame index and frame-start position must match the accepted display request's resolved frame identity. `seekToPosition(totalDuration)` resolves to the final frame index and final frame start position and is not answered with end of sequence.

Frame-handle and application failure-handle ownership transfers only when event submission is accepted, before asynchronous handoff or canonical admission; rejected or closed submissions retain provider ownership. Every accepted handle is released exactly once after rejection by canonical admission, staleness, retained use, render failure, terminal retirement, clear, replacement, undelivered work, or destruction makes it unreachable. A frame handle pinned for `RestorePrevious` is not discardable before commit or restoration resolves the transition; a failure handle remains owned only while the matching `CurrentRequest` or `RestoredTransition` observation exposes its reference. Release follows the public threading contract, never runs on the Qt Quick render thread, is not reentrant with the request that submitted the handle, and completes before its session is destroyed. Dispatch admission is not cleanup completion: ownership and capacity remain retained until the required callback has executed and affinity-bound destruction has finished.

Provider cleanup ownership outlives revocable item delivery until accepted event ingress, frame leases, application failure handles, close delivery, and affinity-correct destruction have converged. Close or shutdown revokes further event acceptance, but destruction waits for ingress already accepted and captured handles to finish release. A provider that transfers a session keeps its QObject affinity dispatch-capable until that destruction completes; provider-controlled affinity shutdown cannot precede the lifetime it enables. Application shutdown destroys viewport items and render resources before crossing the component cleanup-completion boundary, and crosses that boundary before tearing down the application dispatcher or provider affinities. The completion boundary synchronizes only component-owned cleanup and the affinities needed to finish it; it does not depend on broadly pumping unrelated application events. Shutdown prevents further state delivery, retires undelivered handles, and keeps cleanup ownership alive until safe disposal. Factory-result failure-handle release uses the viewport command-processing affinity because no session exists. No particular lifetime-barrier object, acknowledgement representation, or count is required.

Provider session ownership is bounded per role and retains only the newest accepted deferred open when cleanup consumes live capacity. Deferred admission owns no provider session or transferred provider resource and remains waiting without invoking the factory. A newer replacement supersedes it; clear, generation retirement, or shutdown revokes it; and restored capacity invokes the factory only when its generation and role are still current. Cleanup latency alone never creates a generation-terminal provider failure. Exact live-record capacity and storage topology are runtime resource policy.

Provider refinement is auxiliary generation-scoped work owned separately from the accepted display request. Every non-bookkeeping presentation, geometry, device-pixel-ratio, cap, budget, or allocation change that advances demand for a committed provider-backed role marks that role non-current, retires any older auxiliary token for the role, and issues exactly one refinement request for the new revision. The request carries a new active token and the then-current demand for the unchanged target, role, frame, and source logical coordinates. Updating current-payload facts from a commit may advance the revision available to later requests but does not itself schedule work or make that payload non-current. The engine makes one explicit exception after an authoritative target commit: each role whose committed quality is `FirstDisplay` receives one auxiliary request for its current demand. Auxiliary results never trigger this exception recursively. Fixed in-memory roles bypass provider demand scheduling and retain current status until another frame or target is admitted.

The engine admits a matching refinement through the normal preparation and render-commit identities, then swaps payload ownership without changing logical target, ready request status, or playback phase. Unsupported, failed, cancelled, or payload-rejected refinement results retire only the auxiliary token and preserve the committed payload; if the demand remains unsatisfied, `currentForDemand` remains false until a later qualifying demand change or successful refinement. Refinement token failure does not populate display-request-terminal diagnostics. A kind, session, token, or role protocol violation and failure to deliver the refinement command remain generation-terminal because they invalidate the session rather than only the optional detail upgrade.

Provisional payloads are not authoritative commits, retained fallback, or restoration ownership. A later authoritative payload replaces the matching provisional role through normal complete-spread render admission. Terminal failure, cancellation, target replacement, or generation retirement releases affected provisional ownership and cannot promote it into readiness or recovery state.

## Playback

Provider playback uses per-role playback-token identity in addition to display-request identity. Frame-ready events for playback validate against the linked active role request. End-of-sequence events are interpreted by that role's engine playback policy rather than being published as a component target.

In play-once mode, end of sequence selects or promotes the final displayable frame and stops only after that frame is committed for the accepted request or already visible same-generation final-frame pixels are promoted to the accepted display identity. In looping mode, end of sequence wraps to the first frame without exposing an out-of-range requested position.

Stop, seek, loop, clear, replacement, unsupported, and terminal failures retire older playback tokens for their affected role or generation. A role-local playback change does not retire its sibling's token. Late playback events for retired tokens are stale.

## Shutdown

Generation close is idempotent. Clear, generation retirement after presentation-target replacement, generation-terminal failure, item destruction, and engine shutdown converge on the same close path. A prior generation moved into a `RestorePrevious` slot remains open and quiescent until the replacement commits or fails; commit closes it, while failure returns it to active ownership without reopening a session. Closing retires engine token and queued-request state before transport sends best-effort cancellation and close requests. A failure while sending cancellation or close cannot create another component terminal because those commands expect no response and cleanup remains best-effort.

Cancellation acknowledgement is not required for the viewport to proceed. A cancellation event for engine-cancelled or closed work is cleanup acknowledgement only. A provider-originated cancellation for a still-active token that the engine did not cancel reports provider failure.
