# ImageViewport Behavior

`ImageViewport` is KiriView's repository-internal Qt Quick viewport presentation component for caller-supplied image sequences and page roles. It consumes accepted `ImageSequence` page sources, presents a primary page and optional secondary page as one viewport presentation, exposes coherent snapshot state to QML and C++ callers, owns rendering for the accepted presentation target, and leaves source lookup, navigation scope, page selection, page pairing and fallback policy, source identity, decoding, caching, display-store lifetime, predecode policy, and refinement payload production policy to KiriView application code, factories, and provider adapters.

## Sequence Assignment

The viewport is a sequence and presentation-target consumer, not a source-discovery or source-conversion service. It accepts only opaque handles created under [ImageSequence Construction](image-sequence.md) and typed targets defined by [ImageViewport Presentation](image-viewport-presentation.md#presentation-target-replacement).

`setPresentationTarget(target, policy)` is the canonical atomic mutating API for presentation-target and spread replacement. A caller that intends a two-page spread supplies both roles in one command. A target with a secondary role but no primary role is invalid; clear requires both roles to be null.

A valid non-empty caller presentation-target replacement creates a new accepted presentation-target generation and an initial accepted display request for each present role, including when the caller declares the replacement to be a same-target refinement. For `NewTarget`, complete validated construction-time metadata may select frame `0` immediately; unknown or partial provider metadata leaves the target unknown until validated metadata can bind the still-active initial request to frame `0`. `SameTargetRefinement` instead creates its initial requests for the preserved selected targets under its authoritative compatibility metadata. Provider-supplied refinement within an already accepted generation does not create a new presentation-target generation.

Sequence metadata defines one source logical coordinate space for each role within an accepted presentation-target generation. Replacement or refinement payloads for the same target may change delivered raster detail without changing this logical space. The logical size becomes immutable when generation metadata is authoritative; contradictory later provider metadata is a generation-terminal payload rejection. A `NewTarget` generation may establish a different logical size, in which case the viewport recomputes fit, zoom limits, pan bounds, visible rectangles, and coordinate conversion from the new accepted size.

Presentation-target replacement is atomic. The viewport validates the whole command before changing any observable state, accepts the new presentation target and derived presentation state together, chooses retained or empty visible display, and exposes ready display ownership only after the complete target spread is presentable. The transition policy also determines whether terminal replacement failure leaves the failed target active or atomically restores the retained commit. `NewTarget` stops playback for the replaced generation; the new generation starts only through an accepted play command or validated authored autoplay. `SameTargetRefinement` preserves each role's selected target and playback intent across its generation change, but playback for a role waits without advancing while that role's replacement display request is pending.

Retained display content is distinct from the accepted replacement target. `state.request` describes the accepted request; `state.presentation` describes the accepted target presentation; `state.display` describes whether visible pixels are empty, ready for the accepted request and presentation, or retained from an earlier request or presentation identity. Retained display geometry and coordinate helpers use the displayed presentation identified by `state.display.displayedPresentationRevision`, not the newer accepted target presentation. Retained pixels never satisfy the replacement target's readiness, capability checks, playback support, or command admission. A transition whose failure policy is `RestorePrevious` keeps the complete retained commit restorable until the replacement commits or fails terminally; resource pressure cannot discard that commit. If the replacement cannot be admitted while preserving the pinned commit, the replacement fails terminally and the prior commit is restored. Other retained fallback may be discarded under resource pressure, changing only the display to empty placeholder state without changing the accepted request, target presentation, or its terminal/loading status.

Same-target refinement may replace visible payload detail without changing the selected target or source logical size. Caller-supplied refinement is marked with `PresentationTargetTransitionPolicy.replacementIntent: SameTargetRefinement`; provider-supplied refinement is admitted only for the active role request and demand. Refinement preserves fit mode, preferred manual zoom percent, content position where valid, role placement, each role's playback intent, elapsed frame progress, authored loop progress, source coordinates, page bounds, and 100% zoom. A role-set or logical source-size change is a new source contract and must not be treated as same-target refinement.

## Page Roles And Spread Presentation

The viewport presents one accepted presentation target at a time. A presentation target has a required primary role and an optional secondary role. The caller decides which source page belongs to each role and whether a target spread should fall back to a single page.

When both roles are supplied in one accepted presentation-target command, the viewport presents them as one virtual spread canvas. Spread direction controls page placement, and page gap participates in spread bounds.

Pages with unequal cross-axis size are centered within the unrotated spread canvas. After rotation and scaling, image content that is smaller than the viewport frame on an axis is centered on that axis, has maximum content position zero there, and is not pannable there.

A target spread with a secondary role becomes ready only when all required roles can be presented together. The viewport must not expose a partially prepared target spread as ready and must not publish secondary-less geometry for a target that includes a secondary role. `state.request.acceptedRoleSet`, `state.display.displayedRoleSet`, `state.display.targetRoleSet`, and `state.display.phase` identify whether callers are observing retained previous content, an empty placeholder for an uncommitted target, or committed active content; the canonical phase/status combinations are defined in [ImageViewport State](image-viewport-state.md#display-phase-invariants).

For an ordinary still-image request, the provider may offer one complete-frame provisional payload before its authoritative terminal result. The viewport may commit provisional pixels only when every required role can be presented as a complete target spread. Such a commit exposes active display pixels while the request remains loading, never makes a partial spread visible, and does not retire the provider request. A provisional payload or envelope that fails display admission, or provisional pixels that fail render commit, is discarded without making the authoritative request terminal.

Terminal spread projection is deterministic. Loading remains loading while any required role is pending and no required role has failed terminally. Once a role fails terminally, the aggregate cannot return to loading or become ready; it may change only from unsupported to the higher-precedence error, or update tied terminal diagnostics to the primary role's facts, as another already-required role settles. When only one role has the winning status, that role supplies the aggregate reason and diagnostics.

## Snapshot State

The public `state` snapshot is one coherent observation of accepted request, visible display, presentation preferences, per-role request and display facts, metadata, geometry, diagnostics, and revisions. The canonical fields, unavailable values, ownership flags, status/phase combinations, and revision domains are defined only in [ImageViewport State](image-viewport-state.md). In particular, accepted-target readiness and retained or active visible pixels remain separately observable.

## Display Geometry

The viewport owns fit mode, effective zoom percent, preferred manual zoom percent, manual zoom range, content size, content position, maximum content position, pannability, viewport frame, visible spread rectangle, visible page rectangles, per-page item rectangles, coordinate conversion, display rotation, mirror flags, spread direction, page gap, backing background fields, smoothing, mipmap, and looping preference.

Public zoom is physical-pixel-aware. At `zoomPercent: 100`, one source logical pixel in the displayed page or virtual spread maps to one physical display pixel after device-pixel-ratio is applied. Payload raster size, preview scale, SVG raster bucket size, QML image cache behavior, and texture source rectangles do not change the public zoom definition.

The observable transform order is spread construction, quarter-turn display rotation, fit or manual scaling, content-position translation, and horizontal and vertical mirroring in item axes. Explicit preferred manual zoom outside the current manual range is invalid when entered. When an accepted source-size, item-geometry, device-pixel-ratio, or display-limit change later narrows that range, the viewport preserves the preferred manual zoom and clamps only effective zoom and content position into the new valid bounds. A later range expansion restores the preferred manual zoom as the effective manual zoom without another caller command.

When item geometry is non-positive, the viewport exposes no presentable image area for public rectangles or coordinate helpers. Already committed pixels that belong to the accepted request may keep ready request and display ownership, but new target payloads remain render-waiting until positive item geometry allows a commit. Independently, absence of a usable render surface keeps new payloads render-waiting without invalidating otherwise computable geometry. Neither condition is by itself a render failure.

Display-only rotation and mirroring are presentation state. They affect rendering, content rectangles, visible rectangles, hit testing, coordinate conversion, fit, zoom, pan bounds, scroll bounds, display-demand projection, and content-anchor placement without changing source metadata.

Coordinate helpers are deterministic reads of the displayed geometry snapshot and follow the validation contract in [ImageViewport API](image-viewport-api.md#qml-item). They do not use newer target-presentation geometry while retained pixels are visible and do not mutate presentation state, diagnostics, or revisions.

## Requests, Commands, And Playback

Command admission is deterministic. Malformed enum values, invalid public value objects, non-finite numbers, missing required fields in command value types, invalid transition policies, and invalid presentation commands are rejected before capability or failure-scope checks. Coordinate helper inputs use their own non-mutating invalid-result contract. Role-scoped commands addressed to absent roles return ignored-no-request. Intrinsic seek-domain errors are invalid before unsupported-capability or generation-terminal checks.

Role-scoped source commands must name the addressed role. `clear()` stays roleless because it clears the accepted target rather than addressing primary or secondary source content.

Terminal failures have explicit scope. Session-open failure, metadata production failure, malformed or contradictory metadata, provider protocol violation, admitted metadata public-limit violation, accurate metadata proving unsupported sequence content, failure to deliver a response-bearing command to an accepted provider session, and exhaustion of the viewport-owned provider request-token space are generation-terminal. An active timed metadata collection whose count exceeds the public envelope is instead rejected at ingress without retiring its token. Invalid accepted targets resolved after metadata, capabilities that prove unsupported after an operation was accepted with unavailable metadata, authoritative frame payload admission rejection, provider terminal frame-production failure, failure to schedule queued authoritative frame delivery, and failure to commit a required authoritative initial, seek, position, playback, caller-refinement, or presentation-only display attempt are display-request-terminal when generation metadata and provider session remain valid. An authoritative terminal failure after provisional pixels committed removes those non-authoritative pixels and follows the accepted target's ordinary failure transition; provisional pixels are never a restorable previous commit. Ineligible or render-failed provisional candidates preserve the loading authoritative request, and an optional rendering-preference fallback or background-only update cannot create request-terminal failure. Auxiliary provider-refinement production, payload-admission, or display-commit failure preserves an already committed authoritative ready display and retires only that refinement; it does not hide a provider protocol violation, provider command-delivery failure, or other generation-terminal failure. A command rejected as invalid or unsupported before acceptance creates no display request. A later accepted request for the affected role may retire a display-request-terminal failure and recover the target; a generation-terminal failure cannot recover without clear or non-empty presentation-target replacement.

Timed sequences support playback advancement through the same accepted request path as explicit seeking. Each present page role has independent playback state and advancement. Playback for one role waits without accumulating catch-up time while metadata, request queueing, provider work, payload validation, non-positive geometry, or display commit blocks that role; another role may continue advancing.

Authored autoplay is metadata-driven and resolves independently for each present role. A newly accepted role within a presentation-target generation may start playback only when validated authored animation facts declare autoplay for a playable timed sequence; unavailable autoplay metadata for that role is not eligible. Autoplay uses the same request path, role playback phases, retained-display rules, loop policy, and terminal failure handling as an accepted `play(role)` command. Metadata delivery order and another role's autoplay eligibility do not suppress or delay an eligible role.

Provider frame, position, and playback requests carry role-specific `ImageSequenceProviderDisplayDemand` under the schema and stale-result rules in [ImageSequence Provider Protocol](image-sequence-provider-protocol.md#provider-demand-and-payload-values). Returned detail may vary, but it must preserve the accepted logical target and coordinate space and satisfy active admission constraints.

A payload-selection demand change does not retroactively invalidate already committed pixels or reset ready request status. Every non-bookkeeping demand revision for a committed provider-backed role leaves its payload visible with `currentForDemand == false` and issues one auxiliary refinement request; a newer revision retires the older auxiliary request. Publishing updated current-payload facts after a commit may advance request-side demand identity for later provider work, but that bookkeeping change alone neither schedules refinement nor makes the committed payload non-current. As the sole automatic exception, each authoritative `FirstDisplay` payload that commits through a target display request issues exactly one auxiliary refinement request for the then-current demand without requiring another presentation change; a `FirstDisplay` result from that auxiliary request does not recursively schedule another request. A successful matching refinement restores current detail; a failed or rejected auxiliary refinement leaves ready status and committed authoritative pixels unchanged. Fixed in-memory payloads schedule no refinement and remain current across presentation-demand changes. `RequireExact` rejects subsequently offered authoritative inexact payloads from any source; an inexact provisional provider payload is released and ignored without retiring its authoritative request, and the preference does not reclassify previously committed pixels as retained or failed.

Playback defaults to play-once unless authored animation facts declare finite or infinite looping. The caller looping override forces infinite looping when true and otherwise follows authored loop policy. End-of-sequence handling never exposes a beyond-final requested target.

Accepting `play(role)` starts or resumes playback only for that present role. `pause(role)` pauses only that role. A pending request accepted before pause may still update visible content, but the role remains paused. `stop(role)` retires that role's playback-generated pending work and restores its latest non-playback target when one exists. These commands do not change another role's playback phase, loop progress, requested target, or displayed frame.

## Non-Goals

The viewport does not own source discovery or access, application navigation and page-pairing policy, source identity, decoder/cache/display-store/predecode policy, refinement payload production, credentials or sandbox policy, gestures, stepped reading movement, snapping, or application command routing. Those concerns remain behind caller and provider boundaries and cannot be introduced through viewport source or rendering APIs.

The viewport validates public sequence and frame metadata before presentation. Malformed dimensions, invalid timing, unsupported payload shape, oversized payloads, and unsafe diagnostic text are rejected or redacted through public status and diagnostics rather than exposed as undefined behavior.
