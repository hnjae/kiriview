# ImageSequence Provider Adapter

The provider adapter is the repository-internal extension point through which KiriView exposes application-owned image sources. It lets the application expose decoding, storage, cache, predecode, refinement, or streaming services as an `ImageSequence` without giving `ImageViewport` direct access to files, URLs, provider URLs, image-provider ids, archives, arbitrary JavaScript objects, display-store entries, or application navigation policy.

Provider-backed sequences are individual page sources from the viewport's perspective. The provider receives viewport requests and supplies typed provider events, declared facts, and complete-frame payloads for viewport demand; it does not own caller navigation policy, spread pairing, page-role selection, application source-identity policy, presentation-target transition intent, viewport presentation state, public diagnostics, scene graph resources, or QML image load acknowledgement.

## Construction Contract

A repository-owned provider must be implementable using only the supported component interface in [ImageViewport Component Boundary](image-viewport-component-boundary.md). Viewport private headers, engine controllers, provider transport internals, render adapters, scene graph resources, and native texture handles are not part of the provider contract.

`ImageSequenceProviderAdapter` is an abstract QObject-compatible type. It exposes one construction method, `descriptor()`, returning `ImageSequenceProviderDescriptor`. The descriptor's canonical `constructionMetadata`, `threadingContract`, and `sessionFactory` fields are defined in [ImageSequence Provider Protocol](image-sequence-provider-protocol.md#sequence-construction-values). Construction-time data is side-effect-free and authoritative for generations created from the sequence.

Construction-time and runtime metadata describe the source logical page space, not necessarily the raster dimensions of every payload that will be returned later. Source logical size is stable geometry input for fit, zoom, pan, spread placement, coordinate conversion, and 100% zoom. Payload raster size is per-frame delivery metadata and may differ from source logical size for preview, first-display, bounded-detail, resolution-independent, or refinement workflows. The canonical demand and payload envelope schemas are defined in [ImageSequence Provider Protocol](image-sequence-provider-protocol.md#provider-demand-and-payload-values).

The general factory outcome and atomicity contract is defined in [ImageSequence Construction](image-sequence.md). Provider-backed construction adapts a descriptor into an opaque `ImageSequence`; expensive probing, network access, archive access, decoder startup, cache population, or payload production begins only after a viewport accepts the sequence and opens a session.

Constructed sequences and active sessions remain deterministic after the original adapter QObject goes out of scope, so the descriptor's stored session factory must retain every dependency it needs independently of that object. The same provider-backed `ImageSequence` handle may be accepted concurrently by multiple viewport instances or page roles; its factory must tolerate concurrent invocation from their command-processing threads, and each invocation must return an independent `ImageSequenceProviderSessionFactoryResult` for one accepted role generation. `ImageSequenceFactory` rejects structurally invalid descriptors with `InvalidProviderDescriptor` without invoking the factory. A failed, malformed, or non-independent session result discovered only when the factory is invoked affects that generation alone and reports provider failure; it does not retroactively invalidate the sequence handle or other sessions.

The viewport maintains bounded per-role capacity for provider sessions whose affinity-correct lifetime has not finished. Cleanup retained solely for a retired generation cannot turn the newest accepted provider-backed generation into terminal failure. When that cleanup temporarily occupies every live-session slot, the newest accepted open remains provider-waiting in one bounded deferred-admission slot without invoking its session factory. A newer replacement, clear, or shutdown retires deferred admission through the same generation authority rules as ordinary provider work, and capacity becoming available invokes the factory only when that deferred generation is still current. Provider factory failure and malformed factory results retain their ordinary generation-terminal behavior after invocation.

## Session Requests

`ImageSequenceProviderSession` has one request entry point: `request(const ImageSequenceProviderRequest&)`. Request values, request kinds, token fields, and display-demand fields follow the canonical schema in [ImageSequence Provider Protocol](image-sequence-provider-protocol.md).

Metadata requests ask for generation metadata. Frame requests ask for a resolved frame. Position requests preserve the public requested position and include the metadata-resolved frame identity needed for payload validation. Playback requests use a playback token and may return frame readiness or end-of-sequence. Frame, position, and playback requests carry `ImageSequenceProviderDisplayDemand`. Cancel and close requests are best-effort provider lifecycle requests; the viewport retires the generation before delivering close and does not depend on a close acknowledgement.

Display demand is advisory input for payload selection and mandatory input for stale-result validation. Providers must follow the canonical protocol's exactness, cached-reuse, envelope, metadata, identity, limit, token, and demand-revision admission rules; returning detail that violates any of those rules is not allowed.

Every metadata, frame, position, or playback request carries an opaque token generated by the viewport. Providers echo request tokens according to the protocol and do not infer ordering from pointer identity, callback order, or object lifetime. Tokens are scoped to the provider session and remain unique within that session while late events can arrive.

Session entry points are called according to the descriptor threading contract. `AffinityBound` calls entry points on the session QObject affinity. `ThreadSafe` permits the viewport-owned command-processing affinity to call entry points directly. QObject destruction still occurs on the session affinity for both contracts.

`Close` is the session quiescence boundary. Before its entry point returns, the provider must stop starting event emissions for that session and detach or synchronize facilities that could access the session QObject afterward. An event emission that started before `Close` returned may finish as a late event; the viewport still admits its ownership transfer for cleanup and applies the normal stale-event rule. The viewport delivers `Close` asynchronously with respect to public viewport progress and does not wait for provider cleanup on the caller's command path.

## Provider Events

The session reports one signal: `providerEvent(const ImageSequenceProviderEvent&)`. Event values, event kinds, unsupported causes, and token echo rules follow the canonical schema in [ImageSequence Provider Protocol](image-sequence-provider-protocol.md).

Terminal events carry typed failure information only. A failed event may include an opaque application failure handle whose reference KiriView resolves through the provider boundary; the viewport retains and releases the handle without interpreting its application detail and derives its own diagnostic text from the admitted event kind, typed failure cause, and failure scope. Waiting and progress are advisory; the viewport may coalesce or drop stale progress events. A provider may emit `providerEvent` from a provider-controlled worker thread; the viewport serializes event admission before changing component state. Event/request compatibility, terminality, duplicate-event behavior, and exact-once failure-handle release follow the canonical protocol and must not depend on emission thread or signal delivery timing.

Frame-ready events transfer ownership with `ImageSequenceProviderFrameHandle` plus `ImageSequenceProviderFrameEnvelope`; borrowed raw `ImageFrame*` results are not supported. The handle is the sole provider-visible payload lifetime boundary, and its exact-once release, affinity, non-reentrancy, and session-destruction ordering follow the canonical contract in [ImageSequence Provider Protocol](image-sequence-provider-protocol.md#provider-demand-and-payload-values).

Primary and secondary page-role sessions use the same request and event channel. Role selection changes viewport aggregation and page placement; it does not restrict which provider event kinds are valid.

## Metadata And Payload Semantics

Metadata-ready events are complete for the selected timing model. They provide frame count, sequence-wide source logical size, frame seek support, position seek support, timed playback support, seek bounds, timing data, and authored animation facts when available.

A still timing model exposes one indexed frame, frame seek support true, frame seek bounds `0..0`, no public duration, position seek support false, and timed playback support false. Timed frame intervals are half-open integer millisecond intervals, start at zero, are contiguous, have positive duration, and derive total duration from the exclusive end of the final interval.

Frame-ready events must match validated sequence metadata and the active demand revision. The handle's `ImageFrame` source logical size must match sequence metadata; its payload facts must describe a finite positive complete-frame mapping whose aspect is compatible with the source logical page after orientation normalization. The envelope's frame index and frame-start position for timed sequences must match the accepted request's resolved frame identity. Payload raster size may differ from source logical size. `seekToPosition(totalDuration)` resolves to the final frame index and final frame start position; it is not an end-of-sequence event.

Provider metadata failure classification is deterministic. Unsupported sequence content maps to generation-terminal unsupported request state. Unsupported operations or capabilities for otherwise valid content map only to the active operation that required the capability. Malformed metadata, construction-time contradiction, protocol violation, or public-limit violation maps to generation-terminal error with payload rejection. Metadata production failure maps to generation-terminal error with provider failure.

For initial, seek, position, and playback display work, frame production failure maps to display-request-terminal provider failure. A well-formed payload that cannot satisfy the active exactness requirement, or that the provider explicitly reports as unsupported, maps to display-request-terminal unsupported with payload rejection. Malformed frame or envelope facts, missing required byte-size data, invalid payload raster size, invalid source-to-payload mapping, resolved-frame mismatch, timing mismatch, and source-logical-size mismatch map to display-request-terminal error with payload rejection. The same outcomes on an auxiliary provider refinement retire only the refinement and preserve an already committed ready display as defined by the canonical protocol. A protocol violation on a still-active token, failure to deliver a response-bearing provider command, or exhaustion of the viewport-owned request-token space is generation-terminal error; command-delivery failure includes auxiliary refinement commands, while failure to schedule queued frame delivery remains display-request-terminal because the session is still usable. Stale events for retired tokens are ignored under the canonical protocol.

Cancellation and close are advisory. A cancelled request may still complete later, but late events are ignored if the viewport has already accepted a newer request or closed the session. Clear, replacement, item destruction, or terminal provider failure must not be blocked by provider cleanup.
