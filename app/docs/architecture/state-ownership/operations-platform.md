# Operations And Platform Effects

- Deletion and Open With file operations: the displayed-media operation planning owner derives the current media target, deletion target, and post-delete follow-up inputs from one committed mixed-media session snapshot. Deletion policy chooses the deletion target and post-delete follow-up target from document and navigation snapshots. File-operation runtime owners handle KDE confirmation, the shared file-deletion and Open With side-effect providers, cancellation and failure handling, notifications, and applying the follow-up plan. Direct-media deletion fallback is a session-owned plan, but the deletion runtime owns the candidate-loading lifecycle used to build that fallback and must reject stale candidate or file-operation completions before returning a completion to the session. Displayed-media target planning must consume source capabilities supplied by the location and media-entry source boundaries, including whether the current media item or unsupported-video placeholder has a desktop-openable URL, a local containing folder target, a user-readable copy path, or only a collection-level deletion target. CBR/RAR and other internally readable but not desktop-openable entries must be represented as unavailable for Open With, copy-path, and containing-folder actions instead of being rediscovered from backend implementation details. KDE/KIO operation failures cross those provider boundaries as typed values with operation kind, target URL, raw KJob/KIO error code when available, cancellation status, user-facing text, diagnostic detail, and retryability rather than as raw strings. Retryable means that the unchanged operation can plausibly succeed after recovery of a transient backend, service, connection, or runtime condition; a central operation-aware classification marks only recognized transient raw errors retryable, while cancellation, request validation, authentication or access denial, malformed or unsupported input, recognized permanent errors, and unknown codes are not retryable. Removal fallback for an image-document page or comic-book container disappearing from its candidate set is a navigation policy consumed by both live candidate refresh and image-document deletion. Ordinary direct media deletion fallback remains document-session owned.
- Deletion transaction: an accepted deletion plan binds one target to the current session, source, and candidate lifecycle identities and admits at most one destructive side effect. The action runtime disables both deletion routes while that transaction is pending. Cancellation and failure leave the accepted session unchanged; success invalidates the deleted target before applying the matching fallback as one session transaction. A completion for a superseded session or source may release operation resources but must not mutate the newer session or dispatch its stale fallback.
- System runtime state: the system runtime owns desktop-environment observer lifetime and platform probes, including power-saver portal subscription state, system animation capability including disabled or reduced-motion state, physical-memory discovery, Flatpak sandbox access facts, portal-granted file access, host thumbnail-cache availability, session-local KIO-backed playback mount availability, and Flatpak multimedia runtime availability for video playback initialization. Runtime domains that need animation policy, file listing, deletion write access, thumbnail-cache sharing, direct-video playback path resolution, or multimedia playback initialization must consume those facts through owned capability boundaries instead of probing the desktop environment or broadening sandbox permissions independently. Memory-sensitive runtime owners and cache or scheduling policy consume the shared system-memory facts instead of probing physical memory independently.
- Owner bypass rule: once a durable public value has a named owner, production facades must not expose public mutators, writable QML properties, direct event-filter dispatch, or alternate APIs that bypass that owner. Production callers use the declared command or observation boundary.
