# Media Runtime Owners

- Document and image loading: the document-session state owner holds current document kind. The image-document runtime owns selected and displayed application source identity, pending navigation target identity, pending load identity, active source and decode jobs, decoded provider resources, transition policy, and user-visible load/error projection. Its ImageViewport integration owner adapts those facts and opaque dependency correlation at the supported boundary without becoming a second image-document or presentation-state owner. Primary image load failures cross the document load boundary as typed values with source and load-lifecycle identity, failure kind, user-facing text, diagnostic detail, severity, and retryability rather than as raw strings. Provider failures cross the dependency boundary only through its supported protocol; the ImageViewport integration owner resolves an opaque application reference only from a matching public observation, and the application failure registry follows supported ownership callbacks.
- Video source loading: the video source-load owner holds playback source preparation, opened-collection source-device acquisition, source-device lifetime, playback-preparation cleanup, pending preparation identity, and backend source clearing. The video-document state owner holds ended-playback state and the public video source, status, and error values. Direct video URLs may resolve through the direct-video playback-preparation boundary. Opened collection videos may receive a media-entry-source-owned playback device only when collection access publishes playable-entry capability; other supported archive video entries remain navigation rows represented by unsupported-video placeholders. Opened collection videos must not pass through direct-media URL resolution or direct-video navigation-source restoration. A natural playback end is a video playback state for the current accepted source, not a source-clear or document-empty transition. Source-load failures and backend playback failures must cross their runtime boundaries as typed values with source identity, failure kind, user-facing text, diagnostic detail, severity, and retryability rather than as raw backend strings. The video-document state owner publishes only the typed user-facing text; backend, platform, archive, and Qt details remain diagnostic payloads for observability.
- Video playback controls: the video playback-control owner holds readiness, control presentation mode, auto-hide eligibility, timeline seekability, timeline value projection, drag-scrub arbitration, session mute state, and play/pause/seek command gates for the active video source. It derives shared behavior from a coherent view of viewport geometry, accepted input modality, and the system animation or reduced-motion capability. QML owns visual reveal and animation transients, reports the required viewport and input-modality facts, and renders the resulting projection; it must not classify shared floating-versus-fixed behavior, overwrite accepted playback position during active scrubbing, keep stale error text after accepted state changes, or route video commands outside the video-document owner.
- Image load sessions: the image loading boundary owns pending load identity, first-display decode context, image-page-scope context, and the resolved image URL for direct archive or directory opens. Page-scope candidate completion must update the accepted session state; no completion payload or collaborator may establish a second resolved URL beside the session-owned image URL.
- Collection source and displayed page identity: for a directly opened archive or directory, the selected container and opened-collection scope remain the accepted source identity while candidate resolution determines the page eligible for display. That page becomes the displayed image identity only through a matching committed-display observation and never replaces or aliases the selected container identity.
- Embedded metadata parsing: the Rust support static library's [embedded-metadata capability](../rust-support-boundary.md) parses image decode bytes and direct video local paths into plain embedded-metadata values. The consuming document runtime owns request timing, source-backend selection, stale-completion rejection, document-level storage, and QML-facing media-information row models. Opened collection video source devices are not metadata inputs. Parser failures are empty metadata results, not document load failures.
- Animated image sources: KiriView provider resources own source-specific reader lifetime, frame decode or composition, normalized timing metadata, payload production, typed source failures, and the application source lifecycle. The Rust support static library's [APNG capability](../rust-support-boundary.md) owns capability-local stream state, animation metadata, frame controls, and raw RGBA8 subframe decoding. Provider sessions expose metadata and frame results through the supported provider protocol and must not create a competing application-owned presentation clock.
