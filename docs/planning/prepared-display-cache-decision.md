# Prepared-Display Cache Decision

Date: 2026-07-07

Decision: Do not build a shared prepared-display cache now. The existing page-local raster refinement cache, in-flight refinement coalescing, display-store reusable handles, and predecode cache already cover the measured duplicate-work paths with lower ownership risk. Milestones 15 through 18 remain skipped unless future profiling shows repeated expensive prepared-display work after these mechanisms have had a chance to hit.

## Threshold

Build a shared prepared-display cache only if a focused measurement or profile shows repeated expensive decode/refinement for the same compatible display-scope key after the existing mechanisms run. Qualifying evidence would include duplicate worker schedules for an identical refinement cache key across compatible owners, repeated foreground data load or decode when a predecode hit should be available, repeated display-store reusable misses for the same compatible reuse key, or material user-visible latency/memory churn that the page-local cache and display-store handles cannot address.

The current threshold is not met. The focused measurements below show zero duplicate worker schedules in page-local revisit and in-flight revisit scenarios, display-store same-key reuse with one stored entry, predecode promotion without foreground data load, and opened-collection repeated navigation without additional data or candidate loading after predecode.

## Measurement Command

`devenv shell -- env LC_ALL=en_US.UTF-8 LANG=en_US.UTF-8 ctest --test-dir target/devenv/cpp-tests -R '^(test_imagepagesurfacecontroller|test_displayimagestore|test_imageloader|test_predecodecache|test_imagedocumentruntime)$' --output-on-failure --parallel 7`

Result: 5/5 focused CTest targets passed.

## Conclusion

The measured duplicate-work paths are already covered where the current architecture intentionally permits reuse. The remaining unmeasured opportunity is cross-owner prepared payload sharing after a page-surface owner has lost its local refinement cache or when primary and secondary roles independently prepare compatible bytes. That opportunity is not enough to justify a new shared owner yet because it would add byte-budget, lease, stale-rejection, display-source acknowledgment, and page-role ownership rules that are currently local and well tested.

M15 through M18 should stay skipped for this plan. Continue with M19 display-store indexing, which improves an existing shared owner without adding a new prepared-display cache layer.

## Reopen Conditions

Revisit this decision if future profiling or focused tests show repeated `raster display refinement scheduled` events for identical compatible cache keys across page-surface owners, repeated foreground decode or data load despite an available matching predecode entry, high-frequency display-store reusable misses for equal keys, or a user-visible latency/memory regression that remains after display-store indexing.
