# Rendering

Rendering must translate prepared image payloads and viewport presentation state into encapsulated render updates. Backend selection is ImageViewport architecture, not caller policy, and the public API must not expose scene graph ownership, QML image-provider URLs, load acknowledgements, render-frame projections, or backend resource lifetimes. The render boundary admits prepared CPU-backed complete-frame payloads only; native texture payloads, tiled payloads, caller-owned scene graph resources, and caller-owned Qt Quick image items are outside the end-state contract and must not participate in request state, payload admission, or scene graph ownership.

Presentation geometry is owned by the engine and specified in [Presentation Geometry](presentation-geometry.md). Rendering consumes the engine-authorized geometry projection and must not reconstruct canonical fit, zoom, pan, spread, rotation, mirror, visible-rectangle, or coordinate-conversion state from render-local resources.

## Render Data Flow

Prepared frame payloads carry source logical page size, complete-frame payload raster size, source-to-payload mapping, alpha information, timing identity, orientation identity, page-role identity, quality identity, and any internal payload policy identity required by the installed backend. Source logical page size is the orientation-normalized image size used for page geometry, spread geometry, coordinate conversion, 100% zoom, and displayed page size; payload raster size and backend source rectangles remain render details. Lower-detail, first-display, bounded-detail, and refinement payloads may differ in raster size while preserving the same source logical page-space contract. Frame preparation normalizes each oriented payload into source logical page-space before render admission and geometry publication, so render adapters receive a single page-space contract instead of independently interpreting image I/O orientation policy or `QImage::devicePixelRatio()`. Full color-management policy is not part of the public viewport contract; internal color tags must not change public geometry, status, coordinate conversion, or request ordering. The render adapter receives prepared role payloads plus a viewport-owned presentation snapshot: viewport frame, virtual spread canvas, per-role spread rectangles, item-space mapping, source rectangles, horizontal and vertical mirror flags, smoothing, mipmap request, background state, fit mode, physical-pixel-aware zoom percent, content position, spread direction, page gap, normalized quarter-turn rotation, and scan-derived placement.

The adapter must create or update scene graph resources only on the appropriate Qt Quick synchronization/render path. GUI-side cleanup must invalidate logical render state without dereferencing raw scene graph pointers after ownership has moved to the render side.

Render planning is a pure value step before scene graph materialization. It derives background primitives, ordered role layers, payload identities, unrotated target rectangles, physical source rectangles, rotation and mirror transforms, quality requests, and pre-materialization failure intent from the engine-authorized snapshot without allocating scene graph nodes, textures, or other backend resources. Scene graph materialization consumes a known valid plan, performs backend allocation, and reports only allocation or backend-specific failures that cannot be known during pure planning.

Callers must not own, inject, retain, or compare scene graph resources for viewport display. The public `ImageViewport` item encapsulates all render resources behind viewport state, commands, revision tokens, and render acknowledgements. Provider adapters and sequence factories supply source metadata, display-demand-aware complete-frame payloads, and diagnostics, not scene graph objects, QML provider URLs, load acknowledgements, or backend resource handles.

Frame handles remain provider-visible lifetime boundaries even after rendering ownership moves into the viewport. The viewport may retain a handle while its payload is visible, retained as fallback, pending render commit, or needed for playback continuity; it releases the handle exactly once when no public or retained display state can reference that payload or when memory pressure discards retained payloads. Render failure releases the failed payload unless the engine chooses to retain an older committed payload as visible fallback.

Retained fallback display keeps the presentation snapshot that produced the retained geometry. New accepted presentation state may advance while retained pixels remain visible, but displayed geometry, coordinate helpers, and render synchronization for those retained pixels continue to use the retained display presentation identity until new target payloads commit or retained display is cleared.

Render data is immutable for the duration of one synchronization attempt. Payload data, target spread data, and presentation data have separate identities. Payload changes require new prepared payload identities and payload commit acknowledgements; a two-page target spread requires acknowledgements for the complete role set before ready display ownership is published. A render failure for any required role is reported as a role-scoped acknowledgement to the engine and must not publish a partial spread; the engine owns aggregate target-spread terminal projection and the transition-selected retained or empty visible display state. Presentation-only changes reuse the latest committed payload identities and advance presentation/display revision tokens without resetting request readiness. A pending provider payload may be rendered from a synchronization snapshot before it is public display content; only the accepted render commit acknowledgement promotes that payload or complete target spread to ready request/display ownership.

Render acknowledgements identify the target spread plus every required role payload identity for that snapshot. A commit acknowledgement is complete only when all required role identities match the engine's active target spread, and a failure acknowledgement carries the failed role identity so stale or non-required role failures can be discarded without changing newer request or display state.

Render failure acknowledgements carry an internal cause selected at the render boundary, such as missing scene graph window, texture creation failure, image-node creation failure, invalid role payload, or unknown backend failure. The cause is for internal diagnostics and operational attribution only; public request projection is bounded `Error` with `RenderFailure`.

The engine-authorized render snapshot owns the ordered role layer list for a synchronization attempt: prepared payload identities and upload-ready image data, source rectangles, target rectangles, mirror flags, quality requests, background presentation, and presentation mapping. Item-side synchronization adapts that snapshot to the render adapter input contract and supplies Qt Quick ownership handles such as the previous node and window; it must not query live sequences, requested/displayed frame state, provider state, or mutable display payload fields to assemble or repair layers after snapshot creation.

## Quality Requests

Smoothing and mipmap settings are caller presentation preferences. The render boundary must treat inability to satisfy an optional quality request as a presentation fallback, not as payload rejection or request failure. If the fallback is observable, the engine owns the warning lifetime and display revision effect; correctness and caller branching continue to depend on status, reason, capability, and geometry observations rather than advisory warning text.

## Background

Transparent, solid color, and checkerboard backgrounds are item backing presentation. They fill the local item bounds behind image content and do not contribute to content geometry, image coordinate validity, or request readiness.

Background rendering is independent of payload admission. A background-only update must not advance request status, display frame, displayed position, or playback phase.

Background mode, background color, mirroring, fit mode, zoom percent, content position, spread direction, page gap, quarter-turn rotation, scan position, pannability, and observable quality fallback are presentation-affecting display changes. They update the display revision token even when the committed payload identities are unchanged.
