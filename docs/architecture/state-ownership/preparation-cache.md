# Preparation And Cache

- Active navigation thumbnail strip: the top-level C++ document session owns the QML-facing thumbnail-strip projection derived from the same confirmed active navigation list as the toolbar readout. Thumbnail activation is a session active-navigation command using the projected row identity or active-navigation number; QML must not derive or open direct media, archive-entry, or collection targets from thumbnail model data. A thumbnail runtime owns source adaptation, demand handling, async lifecycle, stale-completion rejection, result projection, and `QImage` or image-provider storage for the active strip. QML reports visible demand and renders projected thumbnail or fallback results, but it must not schedule thumbnail work, resolve source renderability, or independently list sibling directories, archive entries, or image-document candidates. Source adapters define source identity, renderability, cache identity candidates, and freshness facts. Rust may compute plain thumbnail cache policy from value snapshots, but it must not own the live `QImage` cache or eviction bookkeeping.
- Preparation and cache: C++ owns prepared image objects, decoder jobs, display image entries, memory pressure handling, and cache lifetime. Rust may compute preparation priority or eviction policy from plain metadata, but cached runtime objects remain in C++.
- Ordinary direct media predecode: the C++ document-session media-predecode runtime owns the predecode/cache lifetime for mixed image/video direct media scopes. It owns the media predecode coordinator, schedule/cache eligibility checks, cancellation, clear behavior, cached predecoded-image lookup, and the conversion of committed session facts into coordinator schedule context. The session runtime may supply the current direct-media activity flag, cursor URL, active image/displayed predecode facts, and first-display decode context from its committed session and leaf snapshots, but it must not own the predecode coordinator lifecycle or duplicate schedule/cache eligibility. Session-owned direct media predecode has its own decode, power-saver, timer, thread-count, and cache-budget dependency boundary instead of borrowing image-document runtime dependency ownership. Shared predecode scheduling runtime state, including debounce timers, power-saver reaction, generation acceptance, pending work context, and dispatch of schedule operations, is owned by the C++ predecode runtime. Image and mixed-media coordinators provide only their domain-specific candidate and window planning, receive scheduler/clock and host-thread facts through explicit dependency inputs, and do not probe wall-clock timers or system thread count directly. Any candidate snapshot needed after debounce or power-saver resume must travel inside the pending schedule context instead of beside it. Direct media predecode clear is keyed by the owning predecode scope, not by direct-media navigation refreshes: entering or leaving an ordinary direct-media parent scope clears at most once per accepted scope transition, while current-item changes and repeated refreshes inside the same parent scope must retain provider-ready cached still images. Direct media predecode eligibility is still-image-only: video items may be used as cursor positions for image-predecode priority, but cached runtime objects remain provider-ready still-image display payloads and video frame predecode is not in scope.
- Image-document predecode: the C++ image-document predecode runtime owns still-image predecode/cache lifetime for image-document page navigation scopes, including opened collection scopes. It consumes confirmed page candidate snapshots, the committed displayed image presentation, pending same-scope navigation target facts, first-display decode context, power-saver state, and thread-count facts through explicit inputs. Pending-target changes may reprioritize the predecode window without clearing provider-ready cached images or canceling active navigation solely because the selected image URL changed. Predecode may return provider-ready display payloads to the image load/presentation owner, but it must not publish active navigation, displayed URL, readiness, error state, zoom state, or page selection.
- HEIF source-internal tiling: C++ owns HEIF decoder context and image handles, QImage allocation, and painting requested source rects into one display image while Rust owns tile-grid validation and source-rect tile-region planning from plain numeric tiling metadata. Source-internal HEIF tiling is allowed only inside a decoder or refinement job that assembles one accepted display `QImage`; it must not publish multiple visual page tiles or reintroduce viewport tile scheduling.
