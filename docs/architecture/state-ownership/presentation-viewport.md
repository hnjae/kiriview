# Presentation And Viewport

- Image presentation runtime: the image presentation runtime is the single mutable owner of image presentation state exposed to QML. It owns current presentation mode, right-to-left reading, transition phase, committed image presentation, pending image navigation presentation, zoom workflow state, rotation, logical viewport frame, visible source rect, scan-start handoff, page-slot visibility, provider display-source projections, restoration snapshots, and display refinement demand. Page-slot display source state must be represented as explicit empty, provider-ready, retained-committed, and display-error variants instead of independent image-present and provider-source fields; visible provider-backed projections may only come from provider-ready or retained-committed variants, while display-error variants may remain visible without a provider URL. Rust geometry or spread policy may calculate next values from snapshots, but it must not store a second live copy of those workflow values.
- Image presentation mode transitions publish an explicit phase: previous-active while the last committed presentation is still authoritative, transitioning-placeholder while no partial target presentation may be rendered, and committed-active after the new single-page or two-page spread presentation is complete. The image presentation runtime holds the canonical zoom snapshot, rotation, viewport frame, visible source rect, spread mode, reading direction, primary and secondary visibility, and render projection for the committed mode. Preparing a secondary page may update loader-owned decoded surfaces, but it must not copy zoom into page-surface owners, patch page visible rects, or expose a partially prepared spread as the active public owner. If a transition aborts, the runtime restores from the retained restoration snapshot and leaves the previous committed presentation authoritative.
- Image page surface owners: page-level presentation objects are display-resource owners, not public presentation-state owners. They may retain animation readers, display entries, display-image pin leases, previous-frame retention, image revision, static-image payloads, predecode cacheability facts, and load lifetimes. They must not expose or store mutable zoom mode, zoom percent, rotation, logical viewport frame, visible source rect, page visibility, display-source policy, render-snapshot policy, tile caches, custom render resources, or public transition state. Production APIs must not provide setters that directly write viewport content position, visible item rect, zoom percent, rotation, render-snapshot fields, or tile/render state outside the presentation owner.
- Image viewport frame bridging: C++ owns the canonical logical viewport frame as a revisioned presentation projection. QML owns only Qt Quick item instances, physical `Flickable` content position, pointer anchors, gesture sampling, rebound, and animation state. Presentation commands publish monotonically increasing command revisions with requested content position, content size, image rect, visible item rect, pannability, outcome, and status; QML applies only the latest non-superseded command revision and reports actual physical state back as observations or acknowledgements with their own revision and origin. Gesture, inertia, overshoot, resize, rotation, device-pixel-ratio, and explicit acknowledgement observations may promote physical state into the canonical frame only through the C++ owner. Delayed QML callbacks must not write the logical frame or replay stale content positions.
- QML-facing stale-sensitive revisions are C++-owned. C++ may store revisions as `quint64`, but QML must not create them, store them in numeric `int` or JavaScript `number` properties, compare them arithmetically, or pass them through APIs that can narrow their value. QML may retain opaque token strings minted by the C++ owner and ask that owner whether a projection, claim, or acknowledgement is newer, applicable, superseded, rejected, or accepted.
- Image viewport commands: zoom step, manual zoom, fit mode, fit-or-actual-size toggling, keyboard pan, scan forward/backward, scan-start handoff, and content-position clamping are presentation commands. QML may pass UI-local anchors or deltas into those commands, but it must not calculate the resulting zoom percent, scan target, or canonical content position. The command owner records whether the command was applied, superseded, rejected, or promoted by an observation. Viewport command application must be driven by the command projection revision flow rather than by each individual QML command handler deciding when to apply the projection.
- Fit-mode presentation selection: the image presentation runtime owns the current fit-mode menu selection used by toolbar and menu checked state. Manual zoom may leave the last accepted fit-mode selection available for later fit commands, but QML must consume that runtime projection rather than storing a durable selected-fit-mode mirror or applying optimistic selection before a command is accepted.
- Media viewport composition: QML owns the shared media workspace host that composes the media viewport area with layout-reserving panels. The workspace host owns media-area SplitView layout, runtime-only panel visibility, panel sizing, and the public null-safe interaction surface consumed by shared shortcut wiring. Inside that workspace, the media viewport host selects and loads exactly one active media viewport delegate through the formal delegate contract. The viewport host manages delegate selection, shared viewport focus dispatch, overlay placement, and delegate signal forwarding, but it must call only delegate-contract APIs and must not reach into mode-specific viewport internals. Media viewport delegates own common viewport click and context-menu request forwarding through the shared contract. Image-specific local pan, zoom, spread, and high-level image/provider item instances are owned by the image viewport and facade/runtime stack and are exposed to shared wiring only through the image interaction surface; scan shortcut dispatch is an application command route, not an interaction-surface command. C++ owns display-source policy and display-entry lifetime. QML owns the `VideoOutput` item instance and may report a surface claim containing that item plus its visibility and geometry with a C++-minted opaque claim token, but backend attachment, detach, stale route rejection, destroyed-item weak handling, and public video-output state belong to the session/video runtime owner. Video-specific playback controls, seek handling, and Qt Multimedia integration remain owned by the video document/runtime stack and use the default no-op interaction surface for image-only commands.
- Display-source projection and provider entries are the visual boundary for images. QML high-level image items consume accepted source facts while decode and refinement jobs publish whole display images. QML supplies viewport and scroll inputs only; it must not compute display buckets, SVG scale buckets, provider ids, refinement demands, stale-display fallback policy, or cache retention. Window changes, scene-graph invalidation, DPR changes, and texture-capability changes advance render-context freshness for display-bucket demand rejection, not for app-owned low-level rendering resources.
- View render context: the non-rendering render-context bridge owns document render-context provider attachment, primary-only provider installation, component-completion inputs, scene-change invalidation, display DPR observation, and a conservative or public-API-derived texture cap. It must not draw, implement custom scene-graph rendering, call private or low-level rendering interfaces, own textures, or schedule decode work. Secondary page visuals must not install or clear the document render context provider.
- Display refinement scheduling: the image presentation/page-surface owners translate visible provider-display projections into whole-image display bucket demands, display-source revisions, provider entries, and bounded-detail, unsupported, or failed states when one safe display image cannot represent the demand. Production image display must not schedule visual tiles, maintain decoded tile caches, project render frames, or retain scene-graph render resources.
