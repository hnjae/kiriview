# ImageViewport Behavior

`ImageViewport` is a Qt Quick viewport presentation engine for caller-supplied image sequences and page roles. It consumes accepted `ImageSequence` page sources supplied by the caller, presents a primary page and optional secondary page as one viewport presentation, exposes request, display, geometry, playback, and presentation state to QML, and leaves source lookup, navigation scope, page selection, page pairing and fallback policy, route-transition meaning, action availability, title and deletion policy, archive position, source identity, decoding, caching, and predecode policy to sequence factories, provider adapters, and application code.

## Sequence Assignment

The viewport is a sequence and page-set consumer, not a URL loader. It must not interpret strings, file paths, URLs, archives, byte buffers, JavaScript objects, or raw provider objects as image sources through the `sequence` property or page-set command arguments.

`setPageSet(primary, secondary, policy)` is the canonical atomic mutating API for page-set and spread replacement. A caller that intends a two-page spread supplies both roles in one `setPageSet(...)` command; `primarySequence` and `secondarySequence` are observations of the accepted page set, not independent writable transition inputs and not an ordering mechanism for constructing a spread. The viewport must not expose a transient primary-only accepted page set when one accepted `setPageSet(...)` command supplied both primary and secondary roles.

Assigning a valid non-null sequence through the compatibility `sequence` property is equivalent to `setPageSet(sequence, null, PageSetTransitionPolicy.default)`: it starts a new primary-only accepted page set, clears any accepted secondary role, creates an accepted sequence generation, and creates the initial accepted display request using the default page-set transition policy. Assigning `null` or calling `clear()` clears the accepted request, stops playback, removes retained display content, and returns request and display observations to their empty states.

Assigning a valid non-null sequence also creates the role's initial display request. If a complete validated construction-time metadata set is known for the selected timing model, including public logical image size, timing facts, seek bounds, and capability facts, the initial target is frame `0`; timed sequences also expose requested position `0`, while still-image sequences expose requested position `-1` because they have a frame identity but no public timing identity. Partial construction-time metadata is not enough to issue the initial frame request. If provider runtime metadata is required before a first displayable target can be selected, the generation reports `Loading` with unknown requested frame and position for that role. Validated metadata creates a metadata-bound accepted display request for frame `0` only when the unknown-target initial request is still the active display request for that role; otherwise metadata only updates generation facts and revalidates the current active target. The metadata-bound request becomes the accepted display request, advances public request observations and revision tokens as a new request, and prevents late work for the earlier unknown-target request from changing public state. Initial display selection does not start playback unless accepted authored animation facts make the initial display autoplayable. Autoplay becomes an accepted playback intent for the initial display, reports `Waiting` while metadata, preparation, geometry, or render commit is pending, and consumes sequence time only after the initial target commits as the accepted visible display; otherwise `playbackPhase` remains `Stopped` until an accepted play command.

Still-image sequences expose one indexed frame and no duration. Their public metadata reports frame count `1`, frame seek support `True`, timed playback support `False`, position seek support `False`, total duration `-1`, invalid position seek bounds, frame seek bounds `0..0`, and requested or displayed position `-1`. Seeking to frame `0` is a valid explicit display request; other frame seeks are invalid, position seek and `play()` commands are unsupported, and `pause()` or `stop()` follow the active-request command rules without adding timing support.

For a provider-backed sequence, assignment is accepted before provider startup can make the generation fail. If the provider session cannot be opened after acceptance, the new generation remains observable, reports `Error` with provider failure, and any caller-selected retained display content from the previous generation remains only as visual fallback.

Page-set replacement is a viewport-owned transition transaction. A caller supplies the accepted primary and optional secondary sequences plus page-set transition intent; the viewport validates the whole command before applying any state, accepts the new page set, updates presentation state, chooses retained or empty visible display according to the display transition, hands scan and content position to the new spread, and publishes ready display ownership only through an atomic target-spread commit. Invalid transition intent returns a deterministic command outcome and does not partially replace the page set, reset transforms, clear retained pixels, start provider work, or advance request/display state.

The display transition is caller intent, not a caller-owned display mechanism. `RetainPrevious` keeps the previous ready or retained presentation visible while the accepted replacement loads or fails. `ClearBeforeLoad` clears visible page pixels before replacement loading, so loading or terminal error state for the accepted replacement does not show old pixels. Both modes keep accepted request/status distinct from visible display state. Retained visible pixels never imply accepted target readiness, and entering or leaving retained display advances the display revision token even if the retained pixel payload and presentation mapping are unchanged.

A page-set transition policy also expresses viewport-owned presentation handoff. Zoom transition may preserve the current fit/manual zoom, reset to `Contain`, or preserve the manual percent where applicable; fit-mode transition may preserve the current mode or set an explicit public fit mode. Content-position transition may preserve, clamp, move to the current scan start, or move to the current scan end after the new spread bounds, rotation, and mirror state are known. Rotation transition may preserve the current quarter-turn rotation or reset to `0`. Mirror transition may preserve both axes or reset both axes to `false`. Spread-direction transition may preserve the current direction or set an explicit `LeftToRight` or `RightToLeft` direction. Page-gap transition may preserve the current gap or set an explicit finite non-negative logical gap. The caller supplies these policies as intent only; ImageViewport computes the resulting fit, zoom, pan, scan position, visible rectangles, spread geometry, and clamping from canonical viewport state.

Invalid page-set transition policy fields reject the whole transition before any state is applied. Invalid fields include invalid enum values, missing explicit values for explicit transitions, an explicit fit mode outside the public fit-mode set, an explicit spread direction outside `LeftToRight` or `RightToLeft`, a non-finite or negative explicit page gap, and `zoomTransition: ResetToContain` combined with an explicit resulting fit mode other than `Contain`. The previous accepted page set, presentation state, retained or empty display state, playback phase, request diagnostics, provider work, and request/display revision tokens are preserved exactly as they were before the command; command diagnostics follow the public command-outcome rules for invalid commands.

The default page-set transition policy used by compatibility assignment and two-argument page-set replacement retains the previous display, preserves fit mode and zoom intent, clamps content position into the replacement spread, preserves rotation, preserves mirror flags, preserves spread direction, and preserves page gap. Callers that need a loading blank state, a new-page scan start, rotation/mirror reset, a direction change, or a gap change request those effects in the transition policy rather than issuing ordered follow-up commands after replacement.

Standalone `setSpreadDirection(direction)` and `setPageGap(gap)` commands are for presentation changes outside page-set replacement. They update viewport-owned presentation state only; they do not replace the accepted page set, change accepted request identity, start or cancel provider work, change playback ownership, or change source identity. A caller changing direction or gap together with a new page set uses `PageSetTransitionPolicy` so the replacement, retained-or-empty display choice, and resulting geometry are accepted atomically.

Retained display content may come from an earlier display request in the same sequence generation or from an earlier page-set generation when the transition policy selected `RetainPrevious`. If the accepted replacement reaches a terminal unsupported or error state before committing content, `requestStatus` and request diagnostics describe the accepted replacement, while `displayStatus` reports whether old pixels are retained or the display is empty according to the chosen display transition.

Retained display content is a visual fallback only. The retained `displayedFrame`, `displayedPosition`, displayed image size, and geometry observations describe the pixels still on screen; request status, request reason, command outcomes, playback support, and sequence capabilities describe the accepted replacement. A failed replacement must not appear ready merely because retained pixels are visible, and it must not inherit the previous sequence's capabilities.

Accepted request readiness and visible presentation readiness are separate observable facts. `requestStatus: Ready` means the accepted page set is ready. `displayStatus: Ready` means visible pixels belong to that accepted page set. `displayStatus: Retained` means visible pixels are inspectable but belong to an earlier request while the accepted page set is loading, unsupported, or failed. Commands operate on the accepted request/page set unless a helper is explicitly documented as visible-presentation inspection. When `displayStatus` is `Retained`, controls that issue commands operate on the accepted replacement, diagnostics describe the accepted replacement, and overlays or pixel inspection use the retained displayed geometry. The viewport does not expose accepted or displayed sequence object identity; callers distinguish stale visible pixels through `displayStatus`, request/display status, requested/displayed target observations, and revision tokens.

Sharper same-source replacement is represented as a page-set transition, not as caller-owned zoom or geometry repair. Because source identity is caller-owned, ImageViewport does not decide whether two sequences are the same document source. `replacementIntent: SameTargetRefinement` is a caller annotation that the replacement serves the same selected target; it does not override explicit transition fields. Retain versus clear, fit and zoom preservation or reset, content-position handling, rotation reset or preserve, mirror reset or preserve, spread direction, and page gap are decided only by the corresponding transition fields. Combinations such as `SameTargetRefinement` with `ClearBeforeLoad`, rotation reset, mirror reset, direction change, or page-gap change are valid. ImageViewport still treats the replacement as a new accepted request for public revision and stale-result behavior. Late results from the preview request cannot overwrite the sharper accepted request, and the caller does not recompute zoom, pan, visible rectangles, spread geometry, or scan state in QML.

## Page Roles And Spread Presentation

The viewport presents one accepted page set at a time. A page set has a required primary role and an optional secondary role; supplying only a primary role to `setPageSet(...)` is a single-page presentation, and supplying both roles to one `setPageSet(...)` command is a two-page spread presentation. A secondary role without an accepted primary role is not a non-empty presentation, exposes no secondary page geometry, and is not an addressable playback or seek target until it is accepted as part of a page set with a primary role. The caller decides which source page belongs to each role, whether a target spread should fall back to a single page for cover, wide, last, unpaired, video, unsupported, or policy-specific cases, and which `ImageSequence` or provider-backed page source represents each accepted role.

Provider-backed page roles support the same public provider result channel whether they are accepted as primary or secondary. Metadata readiness, frame readiness, waiting or progress hints, end-of-sequence playback results, unsupported results, cancellation results, provider failures, payload admission failures, preparation failures, and render failures have the same role-scoped public meaning before spread aggregation; the secondary role is not metadata-only and is not a reduced-capability channel.

When both roles are supplied in one accepted `setPageSet(...)` command, the viewport presents them as one virtual spread canvas. Reading direction controls page placement: left-to-right placement puts the primary page on the left and the secondary page on the right, while right-to-left placement puts the primary page on the right and the secondary page on the left. The default page gap is zero; non-zero gaps are explicit presentation state and participate in spread bounds.

The full spread bounds are the authority for fit, zoom, pan, scroll bounds, scan position, content size, content position, visible spread rectangle, hit testing, and item-to-spread coordinate conversion. Each page role also exposes its page rectangle inside the spread, its item-space rectangle, its visible page rectangle, and role-scoped item-to-page and page-to-item coordinate conversion. A coordinate that lies in the gap or outside the requested role is invalid for role-scoped page conversion even when it is valid in spread coordinates.

For a target spread with a secondary role, the active presentation commits only after both role payloads required for that target are ready to present. The viewport must not expose a partially prepared target spread as `Ready` and must not publish secondary-less geometry for a target that includes a secondary role. Visible display while the spread is loading or failed follows the selected display transition: `RetainPrevious` keeps the previous ready or retained presentation visible, while `ClearBeforeLoad` leaves the display empty until the new spread commits. Public request status for a spread is aggregate over the roles required by the accepted target: `Ready` is published only after the complete role set commits, `Loading` is published while at least one required role is still pending and no required role has failed terminally, and a terminal failure from a required role seals the target spread without publishing partial ready geometry. If multiple terminal failures are accepted for the same target, `Error` takes precedence over `Unsupported`; when terminal status ties, the primary role's terminal reason and diagnostics take precedence over the secondary role's reason and diagnostics. If only one role has the winning terminal status, that role supplies the aggregate reason and diagnostics. A primary-only target may commit as a single-page presentation when the caller supplied only the primary role.

`setPageSet(null, null, policy)` and compatibility `setPageSet(null, null)` are accepted clear-style operations. `setPageSet(null, secondary, policy)` is also accepted as a clear-style operation because a secondary role is not a presentable page set without a primary role, but page-role argument validation still applies: the secondary argument must be either an `ImageSequence` or `null`, and any other value is rejected before clearing. After page-role argument validation and policy validation succeed, a clear-style operation ignores the supplied secondary role, clears the accepted request, stops playback, removes retained display content, and leaves request and display observations empty. Page-set transition fields are validated but otherwise have no effect for a clear-style operation: `displayTransition` cannot retain pixels, and fit, zoom, content-position, rotation, mirror, spread-direction, page-gap, scan, and replacement-intent fields do not mutate presentation state while clearing. If the transition policy itself is invalid, the command returns `Invalid` and leaves the prior accepted page set and display state unchanged rather than clearing.

## Display Geometry

The item supports presentation fit modes `Contain`, `FitWidth`, `FitHeight`, and `Manual`. `Contain` fits the full spread bounds inside the viewport item, `FitWidth` fits the spread width, `FitHeight` fits the spread height, and `Manual` preserves the caller-visible manual `zoomPercent` while clamping or preserving content position according to the viewport's pan rules.

Public zoom is physical-pixel-aware. At `zoomPercent: 100`, one logical pixel in the displayed image or virtual spread maps to one physical display pixel after device-pixel-ratio is applied. The item logical scale used for rendering is derived from `zoomPercent` and the effective device pixel ratio; callers must not treat public zoom as a raw Qt Quick item scale.

The viewport owns fit mode, effective `zoomPercent`, manual zoom percent, content size, content position, maximum content position, horizontal and vertical pannability, viewport frame, visible item rectangle, visible spread rectangle, visible page rectangles, coordinate conversion, mirror flags, and scan position. Device-pixel-ratio changes, viewport resize, image size changes, spread page changes, page-gap changes, and rotation changes recalculate fit-derived zoom and geometry. In `Manual` fit mode, the public manual `zoomPercent` is preserved across those changes and the content position is clamped or anchor-preserved by viewport rules.

Display-only rotation is presentation state. Accepted rotation is exposed as `rotationDegrees`, is normalized to `0`, `90`, `180`, or `270`, and affects rendering, content rectangles, visible rectangles, hit testing, coordinate conversion, fit, zoom, pan bounds, scroll bounds, and scan movement. `rotateClockwise(...)` advances the rotation by one clockwise quarter-turn and `rotateCounterClockwise(...)` advances it by one counterclockwise quarter-turn. Callers may decide whether rotation commands are available and when to reset them, but the applied rotation state and all geometry derived from it are viewport state.

Display-only mirroring is presentation state. Horizontal and vertical mirror state is exposed through `mirrorHorizontally` and `mirrorVertically`; both axes are independent and may be enabled together. `setMirrorHorizontally(enabled, anchor)` and `setMirrorVertically(enabled, anchor)` update one axis at a time, preserve the anchor when possible, and affect rendering, visible rectangles, hit testing, and coordinate conversion without changing source metadata.

Rotation and mirror reset during page replacement is expressed through page-set transition policy. `resetView()` intentionally restores only the default view transform: `fitMode: Contain`, contain-derived effective zoom, the default manual zoom demand for that contain fit, and the scan-start content position and scan state clamped to the current spread, spread direction, page gap, rotation, mirror state, and item geometry. With no presentable geometry, `resetView()` stores that default view preference while geometry observations remain empty. It does not change accepted page set, spread direction, page gap, rotation, mirroring, background, quality preferences, playback looping, or authored animation facts. Callers that want a new page set to reset rotation to `0` or reset mirror flags to `false` request those reset transitions atomically with the page-set replacement, or use the public mirror and rotation commands as separate presentation changes when no page-set replacement is being accepted.

`setSpreadDirection(direction)` accepts only `LeftToRight` and `RightToLeft`; `setPageGap(gap)` accepts only finite non-negative logical gap values. Direct property assignment, where exposed by the caller language binding, follows the same value validation and no-partial-apply behavior, while the command-style setters expose `CommandOutcome`. Valid standalone direction or gap changes recompute spread placement, content size, pannability, visible spread and page rectangles, per-page item rectangles, coordinate conversion, scan bounds, and clamped content position from canonical viewport state. With no active request or an empty display, the value is accepted and stored while geometry remains empty until content exists. During loading, the value applies to pending presentation geometry and any retained or current visible geometry without changing the accepted request. On a ready display, it recomputes visible spread geometry. On an unsupported or error request, terminal request status remains unchanged and visible geometry updates only when display content exists. On a retained display, it updates retained visible geometry without making retained pixels accepted-ready.

Setting the current spread direction or current page gap is an accepted no-op with no property notification, command diagnostic change, or revision change. A changed accepted value emits the matching property notification and advances `displayRevision` because public presentation state or geometry changed, even when pixels are unchanged; it does not advance `requestRevision`. Invalid direction or gap values return `Invalid` from command-style setters, preserve the prior direction or gap, geometry, display state, request state, provider work, playback phase, diagnostics, and revision tokens, and do not clear prior command diagnostics.

The viewport exposes geometry observations that let callers position overlays and inspect pixels without duplicating placement logic. Callers can observe the displayed spread content rectangle in item coordinates, per-page item rectangles, visible spread and page rectangles, displayed spread size, per-page displayed sizes, content size, content position, maximum content position, pannability, and conversions between item, spread, and page coordinates.

Image and spread bounds are half-open: valid coordinates include the left and top edges and exclude the right and bottom edges. Coordinate helpers report invalid results for points outside the currently visible image, page, or spread area rather than clamping to the nearest pixel. Mirroring and rotation affect both rendering and coordinate conversion.

Coordinate helpers use real-valued item, spread, and page coordinates in the displayed logical coordinate spaces. A page's valid image domain is `[0, logicalWidth) x [0, logicalHeight)`, after any orientation policy that the public frame metadata declares. The spread domain is the half-open virtual canvas that contains the placed page rectangles and any explicit gap. Helpers do not round to pixel indices. Callers that need a pixel index for inspection use `floor(x)` and `floor(y)` only after a helper returns `valid: true`; values on the excluded right or bottom edge are invalid before rounding.

If the item has non-positive width or height, no new frame or spread can be presented. Valid metadata and frame payloads may be requested and prepared, but a new accepted request that has not committed display content for its accepted identity remains `Loading` with render waiting until positive item geometry allows a render commit. Display status remains `Empty` when nothing was previously committed and `Retained` when previous pixels are retained for the accepted replacement. Existing committed content may remain the current display identity, but coordinate conversion, content rectangles, visible spread rectangles, visible page rectangles, and visible containment checks report no presentable image area while either item dimension is non-positive. `displayedImageSize` and per-page displayed sizes remain the committed payloads' public logical image sizes when display content exists, and are unavailable only when no display content is committed. Resizing to positive dimensions resumes presentation for the latest active request without requiring a new sequence assignment.

If an already-ready accepted request is resized to non-positive width or height without changing the accepted sequence or requested target, request status remains `Ready` and display status remains `Ready`; only geometry observations report no presentable image area. The display revision token changes for the geometry change. If a new accepted request is waiting for its first render commit while the item is non-positive, that new request remains `Loading` with render waiting as described above.

## Requests And Status

The viewport distinguishes the latest accepted display request from the currently committed display content. Request status describes the accepted request; display status describes whether visible pixels are empty, committed for the accepted request, or retained from an earlier request.

Invalid or unsupported commands do not erase the previous accepted request. They return an immediate command outcome, update command diagnostic observations unless that command is explicitly documented to preserve prior diagnostics, and leave request status, accepted target, display status, retained display content, and playback phase unchanged. A failed seek reports the command outcome and diagnostic state while preserving the last accepted requested target and any pending request that is still meaningful.

Command admission is deterministic for calls that reach the viewport command boundary. Malformed enum values, invalid public value objects, non-finite numbers, missing required fields in command value types, and invalid transition-policy shapes are rejected before capability or failure-scope checks. After syntax and type validation, role-scoped commands addressed to a role that is not present in the accepted page set return `IgnoredNoRequest`; for a present role, intrinsic seek-domain errors such as negative frame indices, negative positions, and out-of-range targets under known bounds return `Invalid` before unsupported-capability or generation-terminal checks. Presentation-command domain errors such as non-finite anchors, invalid fit modes, invalid spread directions, and invalid page gaps return `Invalid` before canonical presentation state changes. Command-specific exceptions, such as invalid standalone spread-direction or page-gap setters preserving prior diagnostics, are part of the public command contract.

Public status values are stable enough for QML controls to branch on. Diagnostic strings are presentation text and are redacted, bounded, and plain text.

Terminal failures have explicit scope. Session-open failure, metadata production failure, malformed or contradictory metadata, provider protocol violation, public-limit violation in metadata, and accurate metadata that proves the sequence content unsupported are generation-terminal; they close interest in outstanding metadata, frame, payload-admission, and render results for that generation, and the accepted generation remains failed until the caller clears or replaces the sequence. Invalid targets that were previously accepted while bounds were unknown, unsupported seek modes or playback capability resolved after a request was accepted, provider unsupported results for an active request, display-critical payload admission rejection, frame production failure, and render commit failure are display-request-terminal when the generation metadata remains valid; a later valid explicit seek or playback-selected target may supersede that failed display request. A command rejected because the required capability is already known unavailable is not a display request and does not change request status, request reason, accepted target, or playback phase. Commands after an unsupported or error request therefore use the failure scope: generation-terminal failures reject further display or playback requests until clear or replacement, while display-request-terminal failures keep the generation usable according to its metadata and capabilities. Non-positive item geometry postpones presentation without turning otherwise valid content into unsupported content.

Provider-backed sequences may enter loading while metadata is unavailable. During that state, metadata-derived observations such as frame count, total duration, seek bounds, frame seek support, position seek support, and timed playback support report unknown or unavailable values rather than guessed values. Validated metadata updates those observations without requiring a new sequence assignment; metadata failure moves the accepted request to unsupported or error state.

If the current active frame or position target was accepted while metadata bounds were unknown and validated metadata later rejects that target, the generation remains accepted, playback stops when the target came from playback, and displayed or retained content remains unchanged until a valid target commits or the caller clears the viewport. Authoritative metadata proving the accepted target out of bounds makes the accepted display request report `Unsupported` with `InvalidRequest`; authoritative metadata proving the accepted seek mode or playback capability unavailable makes the accepted display request report `Unsupported` with `UnsupportedRequest`. These are display-request-terminal failures when generation metadata remains valid, so later valid requests may supersede them. If a newer display request superseded that target before metadata arrived, the stale target rejection is ignored.

Unknown metadata uses the public unavailable-value contract from the API spec, so controls can distinguish unknown from zero, false, empty, or out-of-range values.

When multiple waits are true at the same time, the public request reason is projected in this priority order: provider waiting, request queued, upload pending, render waiting. For a spread target, wait flags are combined across all roles required by the accepted target before this priority projection is applied. A terminal unsupported or error reason replaces any waiting reason for the affected request. Command diagnostics are not request reasons.

## Playback

Timed sequences support playback advancement with `play()`, frame seeking, and position seeking when the addressed active role reports the required capability. The viewport has one playback driver at a time; accepting `play(role)` selects that role as the playback driver, supersedes playback advancement for any previously playing role, and leaves other roles at their latest accepted non-playback targets unless the caller explicitly changes them. The singular `playbackPhase` describes that active playback driver. `pause()` and `stop()` are active-request controls that affect playback only when playback is active or waiting; when addressed to a present role that is not the active playback driver, they are accepted no-ops and do not pause or stop another role's driver. Playback advances from sequence timing metadata and authored loop facts, not from fixed wall-clock sleeps as an externally visible rule.

Playback phase is observable as stopped, playing, waiting, or paused. Waiting is visible when playback has been accepted but is blocked on metadata before a target exists, or when playback has accepted a target frame or position but is blocked by request queueing, provider work, preparation or upload ownership, non-positive item geometry, or render commit. Waiting is not reported as paused or stopped unless the caller requested that phase or the request reaches a terminal state.

Playback waiting pauses the playback clock. Elapsed wall-clock time while metadata, request queueing, provider work, preparation or upload ownership, non-positive item geometry, or render commit is blocking is not accumulated for catch-up or frame skipping after the requested frame commits.

Playback defaults to play-once unless authored animation facts declare a finite or infinite loop. When the caller `looping` override is `false`, authored loop policy controls end-of-sequence handling; when `looping` is `true`, the effective user override is infinite looping for the active timed sequence. In play-once mode, reaching the end commits the final displayable frame, sets playback to stopped, and does not report an error. End-of-sequence handling must not clear the display, stop on a blank target, or publish a beyond-final requested target. If the same generation already displays the final frame from an earlier request, the viewport may satisfy the terminal request by promoting that visible payload to the accepted display identity: `requestStatus` becomes `Ready`, `displayStatus` becomes `Ready`, playback becomes `Stopped`, and the display revision token advances if display ownership or status changes even though pixels are unchanged. If the final frame is not already visible for the same generation, the viewport makes the final frame the active display request and keeps playback waiting until that request commits or fails. In effective looping mode, reaching the end advances to the first frame without incrementing position beyond the sequence duration; finite authored loops stop only after the final displayable frame of the final authored iteration commits or is promoted.

Frame indices are zero-based. Seeking to a negative frame index is invalid even before frame bounds are known, and seeking to any frame outside known sequence bounds is invalid. Position seeking uses milliseconds; a position within a frame's half-open time interval selects that frame, and seeking exactly to the total duration selects the final frame. Negative positions and positions greater than total duration are invalid.

Unsupported play or seek commands leave playback phase and the next observable requested frame or position unchanged. A sequence or request that becomes terminally unsupported or erroneous while playback is active stops playback.

`stop()` supersedes pending frame requests that were produced only by playback advancement and makes later results for those requests stale. It does not select image content other than the latest non-playback target for the generation, does not change display content by itself, and leaves `playbackPhase` as `Stopped`. After cancelling a playback-generated target, the accepted request reverts to the latest non-playback target for the generation when one exists; otherwise requested frame and position remain unknown until metadata or an explicit command selects a non-playback target. If `play()` was waiting on metadata and had superseded an unknown-target initial request, `stop()` creates a fresh unknown-target non-playback initial request identity; requested frame and position remain unknown, and later validated metadata may create the metadata-bound initial frame `0` request from that fresh identity. `stop()` does not supersede an explicit seek request that is still active before or after stopping; such a request may still commit display content, but it does not restart playback. When the latest non-playback target belongs to a request identity that an accepted `play()` command already superseded, `stop()` creates a fresh accepted non-playback display request identity for the same target, or promotes already committed same-generation content for that target to the accepted display identity. Results for the superseded request identity remain stale.

`play()` may be accepted while timed playback support is still `Unavailable` when the sequence has not declared timed playback impossible. The playback phase becomes `Waiting`, the requested target remains unknown until metadata can select a frame or position, and elapsed playback time is not accumulated. If an explicit seek or initial display request was active while metadata bounds were unknown, this accepted play command supersedes that request for playback start, makes its later results stale, and clears requested frame and position to unknown until metadata selects the first playable target. If metadata later resolves timed playback to supported, playback selects the first playable target and proceeds through the normal request path. If metadata resolves timed playback to unsupported or contradicts construction-time capability facts, playback stops and the accepted request reports `Unsupported` or `Error` according to the capability or metadata failure.

Playback request ordering distinguishes explicit seeks from playback advancement. Invalid or unsupported commands while looping preserve the next observable requested frame or position; callers do not need an exposed loop-progress counter to interpret public state.

## Authored Animation Playback

ImageViewport owns playback mechanics for authored image animations once the caller or provider has adapted the content into an `ImageSequence`. The caller still owns source selection, decoder choice, cache policy, and whether a sequence is assigned; the viewport owns accepted playback ordering, timing, retained-display behavior, display commits, and stale-result rejection for timed animation frames.

An animated sequence may declare authored animation facts: whether the initial accepted display may autoplay, whether later frames may become ready progressively after the first frame, and whether the authored loop mode is play once, a finite loop count, or infinite. Finite authored loop counts and authored infinite loops are distinct facts; they are not collapsed into the simple caller `looping` override. When the caller/provider marks an accepted initial display as autoplayable, the viewport arms playback with the same request, display, and retention ordering as an explicit `play()` command, but sequence time starts only after the initial target commits as the accepted visible display. If the sequence supports progressive animation readiness, the first frame may commit before all later frames are available; later animation frames still pass through the normal accepted request path and cannot overtake newer accepted page-set, seek, stop, clear, or replacement state.

Caller playback commands remain authoritative user intent. `play()`, `pause()`, `stop()`, seeking, looping override, and page-set replacement supersede or preserve authored autoplay according to the same active-driver and stale-result rules used for timed sequences. Authored playback never exposes ready affordances for an accepted target merely because retained pixels from an older target are visible.

## Presentation Controls

Presentation properties such as smoothing, mipmap request, mirror flags, background mode, background color, fit mode, zoom percent, content position, page gap, spread direction, rotation, scan position, and pannability are viewport state. Sequence assignment and clearing must not reset viewport transforms unless the caller explicitly requests a reset.

The viewport owns presentation commands that would otherwise require duplicating canonical geometry in QML. Standalone spread-direction changes, standalone page-gap changes, anchor-preserving zoom, fit-mode changes, pan by delta, pan to start or end, scan next or previous, clockwise and counterclockwise quarter-turn rotation, axis-specific mirroring, and reset view commands are evaluated by the viewport against the current spread bounds, device pixel ratio, rotation, mirror flags, fit mode, and scroll bounds. Valid fit, zoom, direction, and gap commands are accepted even when no display content exists so callers can set presentation preference before content is ready. Pan and scan commands clamp to the current presentation bounds; when there is no presentable geometry or a scan command is already at the first or last segment, the command is an accepted no-op rather than a diagnostic. Callers issue commands and observe outcomes; they do not compute or store canonical content position, scan position, direction, gap, spread geometry, or scroll bounds independently.

Manual zoom demands are bounded by the installed public display limits. A non-finite, non-positive, or above-maximum manual `zoomPercent` is invalid and leaves the previous zoom state unchanged; the viewport does not silently clamp caller manual zoom into a different canonical value. Fit-derived zoom is computed from viewport geometry and accepted spread bounds, and an oversized render demand for otherwise admitted content reports a render failure or documented quality fallback rather than changing source admission rules. Public content limits reject source metadata or payloads; public display limits reject or fail presentation demands.

Transparent content is inspectable through a deterministic background mode. A checkerboard background affects only presentation behind the image and must not change image geometry, request state, or coordinate conversion.

## Non-Goals

The viewport does not own file discovery, URL selection, network access, archive extraction, directory or archive navigation, active navigation scope, page number, primary page selection, secondary page fallback policy for cover, wide, video, last, unpaired, or other application cases, route transition meaning, shortcut availability, toolbar/action routing, title selection, deletion target selection, archive navigation position, source identity, decoder backend choice, cache backend choice, predecode backend choice, temporary files, permissions, sandbox policy, built-in gestures, or application command routing. Those concerns belong to the generic consuming application, explicit sequence factories, application code, or provider adapters that return `ImageSequence` objects.

The viewport does validate public sequence and frame metadata before presentation. Malformed dimensions, invalid timing, unsupported payload shape, oversized payloads that exceed published limits, and unsafe diagnostic text are rejected or redacted through public status and diagnostics rather than exposed as undefined behavior.
