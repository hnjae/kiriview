# ImageViewport Behavior

`ImageViewport` is a Qt Quick item for displaying caller-supplied image sequences. It consumes an `ImageSequence` object, presents the selected frame inside its item bounds, exposes display, request, geometry, and playback state to QML, and leaves source lookup or decoding policy to sequence factories and provider adapters.

## Sequence Assignment

The viewport is a sequence consumer, not a URL loader. It must not interpret strings, file paths, URLs, archives, byte buffers, JavaScript objects, or raw provider objects as image sources through the `sequence` property.

Assigning a valid non-null sequence starts a new accepted sequence generation and initial accepted display request. Assigning `null` or calling `clear()` clears the accepted request, stops playback, removes retained display content, and returns request and display observations to their empty states.

Assigning a valid non-null sequence also creates the generation's initial display request. If a complete validated construction-time metadata set is known for the selected timing model, including public logical image size, timing facts, seek bounds, and capability facts, the initial target is frame `0`; timed sequences also expose requested position `0`, while still-image sequences expose requested position `-1` because they have a frame identity but no public timing identity. Partial construction-time metadata is not enough to issue the initial frame request. If provider runtime metadata is required before a first displayable target can be selected, the generation reports `Loading` with unknown requested frame and position. Validated metadata creates a metadata-bound accepted display request for frame `0` only when the unknown-target initial request is still the active display request; otherwise metadata only updates generation facts and revalidates the current active target. The metadata-bound request supersedes the unknown-target initial request for request identity, revisions, and stale-result filtering. Initial display selection does not start playback; `playbackPhase` remains `Stopped` until an accepted play command.

Still-image sequences expose one indexed frame and no duration. Their public metadata reports frame count `1`, frame seek support `True`, timed playback support `False`, position seek support `False`, total duration `-1`, invalid position seek bounds, frame seek bounds `0..0`, and requested or displayed position `-1`. Seeking to frame `0` is a valid explicit display request; other frame seeks are invalid, position seek and `play()` commands are unsupported, and `pause()` or `stop()` follow the active-request command rules without adding timing support.

For a provider-backed sequence, assignment registers the new accepted generation before opening the provider session. If the session cannot be opened after assignment, the new generation remains observable, reports `Error` with provider failure, and retained display content from the previous generation remains only as visual fallback.

Replacing a sequence keeps the previous display visible until the replacement commits display content or the caller clears the viewport. If the replacement reaches a terminal unsupported or error state before committing content, the viewport reports the replacement as the accepted request and keeps the previous pixels as retained display content. Retained display content may also come from an earlier display request in the same sequence generation when a newer same-generation request is loading or has failed.

Retained display content is a visual fallback only. The retained `displayedFrame`, `displayedPosition`, displayed image size, and geometry observations describe the pixels still on screen; request status, request reason, command outcomes, playback support, and sequence capabilities describe the accepted replacement. A failed replacement must not appear ready merely because retained pixels are visible, and it must not inherit the previous sequence's capabilities.

When `displayStatus` is `Retained`, controls that issue commands operate on the accepted replacement, diagnostics describe the accepted replacement, and overlays or pixel inspection use the retained displayed geometry. The viewport does not expose accepted or displayed sequence object identity; callers distinguish stale visible pixels through `displayStatus`, request/display status, requested/displayed target observations, and revisions. Entering or leaving retained display increments `displayRevision` even if the retained pixel payload and presentation mapping are unchanged.

## Display Geometry

The item supports contain, cover, stretch, and center placement modes. Placement is computed from the item bounds and public logical image size, then alignment positions the placed image within or across the item, zoom scales around the placed image center, pan offsets in item logical pixels after zoom, and mirroring flips the image mapping around the placed image center.

The viewport exposes geometry observations that let callers position overlays and inspect pixels without duplicating placement logic. Callers can observe the displayed content rectangle in item coordinates, the visible image rectangle in image coordinates, the displayed image size, and conversions between item coordinates and image coordinates.

Image bounds are half-open: valid image coordinates include the left and top edges and exclude the right and bottom edges. Coordinate helpers report invalid results for points outside the currently visible image area rather than clamping to the nearest pixel. Mirroring affects both rendering and coordinate conversion.

Coordinate helpers use real-valued item and image coordinates in the displayed logical image coordinate space. The valid image domain is `[0, logicalWidth) x [0, logicalHeight)`, after any orientation policy that the public frame metadata declares. Helpers do not round to pixel indices. Callers that need a pixel index for inspection use `floor(x)` and `floor(y)` only after a helper returns `valid: true`; values on the excluded right or bottom edge are invalid before rounding. Mirroring maps coordinates around the placed image center and preserves the same half-open validity rule.

If the item has non-positive width or height, no new frame can be presented. Valid metadata and frame payloads may be requested and prepared, but a new accepted request that has not committed display content for its accepted identity remains `Loading` with render waiting until positive item geometry allows a render commit. Display status remains `Empty` when nothing was previously committed and `Retained` when previous pixels are retained for the accepted replacement. Existing committed content may remain the current display identity, but coordinate conversion, content rectangles, visible-image rectangles, and visible-image containment report no presentable image area while either item dimension is non-positive. `displayedImageSize` remains the committed payload's public logical image size when display content exists, and is unavailable only when no display content is committed. Resizing to positive dimensions resumes presentation for the latest active request without requiring a new sequence assignment.

If an already-ready accepted request is resized to non-positive width or height without changing the accepted sequence or requested target, request status remains `Ready` and display status remains `Ready`; only geometry observations report no presentable image area. The display revision changes for the geometry change. If a new accepted request is waiting for its first render commit while the item is non-positive, that new request remains `Loading` with render waiting as described above.

## Requests And Status

The viewport distinguishes the latest accepted display request from the currently committed display content. Request status describes the accepted request; display status describes whether visible pixels are empty, committed for the accepted request, or retained from an earlier request.

Invalid or unsupported commands do not erase the previous accepted request. They return an immediate command outcome, may update command diagnostic observations, and leave request status, accepted target, display status, retained display content, and playback phase unchanged. A failed seek reports the command outcome and diagnostic state while preserving the last accepted requested target and any pending request that is still meaningful.

Public status values are stable enough for QML controls to branch on. Diagnostic strings are presentation text and are redacted, bounded, and plain text.

Terminal failures have explicit scope. Session-open failure, metadata production failure, malformed or contradictory metadata, provider protocol violation, public-limit violation in metadata, and accurate metadata that proves the sequence content unsupported are generation-terminal; they close interest in outstanding metadata, frame, preparation, and render results for that generation, and the accepted generation remains failed until the caller clears or replaces the sequence. Invalid targets that were previously accepted while bounds were unknown, unsupported seek modes or playback capability resolved after a request was accepted, provider unsupported results for an active request, frame payload rejection, frame production failure, preparation rejection, and render commit failure are display-request-terminal when the generation metadata remains valid; a later valid explicit seek or playback-selected target may supersede that failed display request. A command rejected because the required capability is already known unavailable is not a display request and does not change request status, request reason, accepted target, or playback phase. Commands after an unsupported or error request therefore use the failure scope: generation-terminal failures reject further display or playback requests until clear or replacement, while display-request-terminal failures keep the generation usable according to its metadata and capabilities. A zero-size item postpones presentation without turning otherwise valid content into unsupported content.

Provider-backed sequences may enter loading while metadata is unavailable. During that state, metadata-derived observations such as frame count, total duration, seek bounds, frame seek support, position seek support, and timed playback support report unknown or unavailable values rather than guessed values. Validated metadata updates those observations without requiring a new sequence assignment; metadata failure moves the accepted request to unsupported or error state.

If the current active frame or position target was accepted while metadata bounds were unknown and validated metadata later rejects that target, the generation remains accepted, playback stops when the target came from playback, and displayed or retained content remains unchanged until a valid target commits or the caller clears the viewport. Authoritative metadata proving the accepted target out of bounds makes the accepted display request report `Unsupported` with `InvalidRequest`; authoritative metadata proving the accepted seek mode or playback capability unavailable makes the accepted display request report `Unsupported` with `UnsupportedRequest`. These are display-request-terminal failures when generation metadata remains valid, so later valid requests may supersede them. If a newer display request superseded that target before metadata arrived, the stale target rejection is ignored.

Unknown metadata uses the public unavailable-value contract from the API spec, so controls can distinguish unknown from zero, false, empty, or out-of-range values.

When multiple waits are true at the same time, the public request reason is projected in this priority order: provider waiting, request queued, upload pending, render waiting. A terminal unsupported or error reason replaces any waiting reason for the affected request. Command diagnostics are not request reasons.

## Playback

Timed sequences support playback advancement with `play()`, frame seeking, and position seeking when the active sequence reports the required capability. `pause()` and `stop()` are active-request controls that affect playback only when playback is active or waiting. Playback advances from sequence timing metadata, not from fixed wall-clock sleeps as an externally visible rule.

Playback phase is observable as stopped, playing, waiting, or paused. Waiting is visible when playback has been accepted but is blocked on metadata before a target exists, or when playback has accepted a target frame or position but is blocked by request queueing, provider work, preparation or upload ownership, non-positive item geometry, or render commit. Waiting is not reported as paused or stopped unless the caller requested that phase or the request reaches a terminal state.

Playback waiting pauses the playback clock. Elapsed wall-clock time while metadata, request queueing, provider work, preparation or upload ownership, non-positive item geometry, or render commit is blocking is not accumulated for catch-up or frame skipping after the requested frame commits.

Playback defaults to play-once. In play-once mode, reaching the end commits the final displayable frame, sets playback to stopped, and does not report an error. End-of-sequence handling must not clear the display, stop on a blank target, or publish a beyond-final requested target. If the same generation already displays the final frame from an earlier request, the viewport may satisfy the terminal request by promoting that visible payload to the accepted display identity: `requestStatus` becomes `Ready`, `displayStatus` becomes `Ready`, playback becomes `Stopped`, and `displayRevision` increments if display ownership or status changes even though pixels are unchanged. If the final frame is not already visible for the same generation, the viewport makes the final frame the active display request and keeps playback waiting until that request commits or fails. In looping mode, reaching the end advances to the first frame without incrementing position beyond the sequence duration.

Frame indices are zero-based. Seeking to a negative frame index is invalid even before frame bounds are known, and seeking to any frame outside known sequence bounds is invalid. Position seeking uses milliseconds; a position within a frame's half-open time interval selects that frame, and seeking exactly to the total duration selects the final frame. Negative positions and positions greater than total duration are invalid.

Unsupported play or seek commands leave playback phase and the next observable requested frame or position unchanged. A sequence or request that becomes terminally unsupported or erroneous while playback is active stops playback.

`stop()` supersedes pending frame requests that were produced only by playback advancement and makes later results for those requests stale. It does not select image content other than the latest non-playback target for the generation, does not change display content by itself, and leaves `playbackPhase` as `Stopped`. After cancelling a playback-generated target, the accepted request reverts to the latest non-playback target for the generation when one exists; otherwise requested frame and position remain unknown until metadata or an explicit command selects a non-playback target. If `play()` was waiting on metadata and had superseded an unknown-target initial request, `stop()` creates a fresh unknown-target non-playback initial request identity; requested frame and position remain unknown, and later validated metadata may create the metadata-bound initial frame `0` request from that fresh identity. `stop()` does not supersede an explicit seek request that is still active before or after stopping; such a request may still commit display content, but it does not restart playback. When the latest non-playback target belongs to a request identity that an accepted `play()` command already superseded, `stop()` creates a fresh accepted non-playback display request identity for the same target, or promotes already committed same-generation content for that target to the accepted display identity. Results for the superseded request identity remain stale.

`play()` may be accepted while timed playback support is still `Unavailable` when the sequence has not declared timed playback impossible. The playback phase becomes `Waiting`, the requested target remains unknown until metadata can select a frame or position, and elapsed playback time is not accumulated. If an explicit seek or initial display request was active while metadata bounds were unknown, this accepted play command supersedes that request for playback start, makes its later results stale, and clears requested frame and position to unknown until metadata selects the first playable target. If metadata later resolves timed playback to supported, playback selects the first playable target and proceeds through the normal request path. If metadata resolves timed playback to unsupported or contradicts construction-time capability facts, playback stops and the accepted request reports `Unsupported` or `Error` according to the capability or metadata failure.

Playback request ordering distinguishes explicit seeks from playback advancement. Invalid or unsupported commands while looping preserve the next observable requested frame or position; callers do not need an exposed loop-progress counter to interpret public state.

## Presentation Controls

Presentation properties such as smoothing, mipmap request, mirror flags, background mode, background color, zoom, pan, fill mode, and alignment are viewport state. Sequence assignment and clearing must not reset viewport transforms unless the caller explicitly requests a reset.

Transparent content is inspectable through a deterministic background mode. A checkerboard background affects only presentation behind the image and must not change image geometry, request state, or coordinate conversion.

## Non-Goals

The viewport does not own file discovery, network access, archive extraction, decoder selection, temporary files, permissions, or sandbox policy. Those concerns belong to explicit sequence factories, application code, or provider adapters that return `ImageSequence` objects.

The viewport does validate public sequence and frame metadata before presentation. Malformed dimensions, invalid timing, unsupported payload shape, oversized payloads that exceed published limits, and unsafe diagnostic text are rejected or redacted through public status and diagnostics rather than exposed as undefined behavior.
