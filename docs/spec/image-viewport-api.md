# ImageViewport API

This document defines the final public API shape for QML and C++ callers. The concepts below are the public surface the implementation must preserve.

## QML Item

`ImageViewport` is a `QQuickItem` that accepts page-set replacement through `setPageSet(primary, secondary, policy)` using only `ImageSequence` objects or `null`. The primary page role is required for a non-empty presentation, the secondary page role is optional, and the compatibility `sequence` property is a shorthand for assigning a primary-only page set. `primarySequence` and `secondarySequence` expose the accepted page roles as observations; they are not independent writable transition inputs and must not be used as an ordered spread-construction API. A secondary role without an accepted primary role is inert: it does not create an active request, does not expose secondary geometry, and is not an addressable role for playback or seek commands until a primary role is accepted with it through `setPageSet(...)`. Values that are not `ImageSequence` or `null` are not viewport requests: if the binding or C++ call attempts to assign a string, URL, archive, byte buffer, JavaScript object, raw provider object, or other unsupported value through `sequence` or a page-set command argument, the assignment or command is rejected before changing viewport state, existing request and display state are preserved, and request and display revision tokens do not change. Diagnostics for such type-conversion failures belong to the caller language or factory that rejected the input, not to viewport request status.

The item exposes request status, request status reason, command diagnostic reason, display status, playback phase, role-scoped displayed frames, requested frames, displayed positions, requested positions, frame counts, total durations, frame seek bounds, position seek bounds, timed playback support, frame seek support, position seek support, displayed page sizes, displayed spread size, content rectangle, content size, content position, maximum content position, pannability, visible spread rectangle, visible page rectangles, per-page item rectangles, display revision token, request revision token, command revision token, error string, and warning string observations. Primary-only compatibility observations such as `displayedFrame`, `requestedFrame`, `displayedPosition`, and `requestedPosition` alias the primary role. Accepted request readiness is observed through `requestStatus`; visible presentation readiness is observed through `displayStatus`.

The item exposes presentation properties for fit mode, physical-pixel-aware zoom percent, content position, spread direction, page gap, quarter-turn display rotation, smoothing, mipmap request, mirroring, background mode, background color, and playback looping.

The item exposes imperative commands for `clear()`, `play()`, `pause()`, `stop()`, `seek(frame)`, `seekToPosition(milliseconds)`, page-set replacement with transition policy, standalone spread-direction and page-gap changes, anchor-preserving zoom, fit-mode changes, pan by delta, pan to start or end, scan next or previous, clockwise or counterclockwise quarter-turn display rotation, horizontal or vertical display mirroring, and `resetView()`. Commands that can fail return an immediate outcome rather than requiring callers to infer command acceptance from retained display state.

Coordinate helpers map item points to spread points, spread points to item points, item points to role-scoped page points, page points to item points, and test whether a spread or page point is inside the currently visible area. The stable QML signatures include `itemToSpread(x: real, y: real): CoordinateResult`, `spreadToItem(x: real, y: real): CoordinateResult`, `itemToPage(role: PageRole, x: real, y: real): CoordinateResult`, `pageToItem(role: PageRole, x: real, y: real): CoordinateResult`, `containsVisibleSpreadPoint(x: real, y: real): bool`, and `containsVisiblePagePoint(role: PageRole, x: real, y: real): bool`; C++ exposes equivalent methods with real-valued point inputs and the same result fields. Primary-only presentations may expose `itemToImage`, `imageToItem`, and `containsVisibleImagePoint` as compatibility aliases for primary-page conversion. Point conversions return a public coordinate-result value with `valid`, `x`, and `y` fields; failed conversions return `valid: false`, `x: 0`, and `y: 0` so QML and C++ callers can test validity without relying on clamping, NaN handling, or exception behavior.

The stable command signatures include `clear(): CommandOutcome`, `play(role: PageRole = Primary): CommandOutcome`, `pause(role: PageRole = Primary): CommandOutcome`, `stop(role: PageRole = Primary): CommandOutcome`, `seek(role: PageRole = Primary, frame: int): CommandOutcome`, `seekToPosition(role: PageRole = Primary, milliseconds: int): CommandOutcome`, `setPageSet(primary: ImageSequence | null, secondary: ImageSequence | null, policy: PageSetTransitionPolicy = PageSetTransitionPolicy.default): CommandOutcome`, `setSpreadDirection(direction: SpreadDirection): CommandOutcome`, `setPageGap(gap: real): CommandOutcome`, `setFitMode(mode: FitMode, anchor: point): CommandOutcome`, `setZoomPercent(percent: real, anchor: point): CommandOutcome`, `panBy(delta: point): CommandOutcome`, `panToStart(): CommandOutcome`, `panToEnd(): CommandOutcome`, `scanNext(): CommandOutcome`, `scanPrevious(): CommandOutcome`, `rotateClockwise(anchor: point): CommandOutcome`, `rotateCounterClockwise(anchor: point): CommandOutcome`, `setMirrorHorizontally(enabled: bool, anchor: point): CommandOutcome`, `setMirrorVertically(enabled: bool, anchor: point): CommandOutcome`, and `resetView(): CommandOutcome`. `setPageSet(...)` is the only public mutating API that creates an accepted two-page spread; callers that intend a spread pass both roles in one command, and the viewport must not expose a transient primary-only accepted page set for that command. `setSpreadDirection(...)` and `setPageGap(...)` are presentation commands for standalone changes outside page-set replacement; callers that need direction or gap to change together with a new accepted page set use `PageSetTransitionPolicy` so the replacement remains atomic, rather than issuing ordered follow-up setters after replacement. `rotateClockwise(...)` advances `rotationDegrees` through `0`, `90`, `180`, `270`, and back to `0`; `rotateCounterClockwise(...)` advances it through `0`, `270`, `180`, `90`, and back to `0`. `setMirrorHorizontally(...)` and `setMirrorVertically(...)` are independent axis setters; callers that want toggle behavior pass the negated observed `mirrorHorizontally` or `mirrorVertically` value. `setPageSet(null, null, policy)` is equivalent to `clear()` after page-role argument validation and policy validation, and `setPageSet(null, secondary, policy)` is accepted as a clear-style operation after the secondary argument has been validated as an `ImageSequence` or `null` because a secondary role is not presentable without a primary role; validated transition fields do not otherwise mutate presentation state for clear-style operations. Non-`ImageSequence` page-role argument values remain rejected before clear-style handling. Invalid policy fields return `Invalid`, preserve the previous page set, presentation state, retained pixels, playback phase, request revision, and display revision, and publish command diagnostics through the normal invalid-command rules. `CommandOutcome` values are `Accepted`, `Invalid`, `Unsupported`, and `IgnoredNoRequest`.

`PageSetTransitionPolicy` is a public command input value type. Its `displayTransition` is `RetainPrevious` or `ClearBeforeLoad`. Its `zoomTransition` is `Preserve`, `ResetToContain`, or `PreserveManualPercent`; `PreserveManualPercent` preserves the canonical manual zoom percent for use when the resulting fit mode is `Manual`, while non-manual resulting fit modes still derive effective zoom from their fit rules. Its `contentPositionTransition` is `Preserve`, `Clamp`, `ScanStart`, or `ScanEnd`. Its `rotationTransition` is `Preserve` or `Reset`. Its `mirrorTransition` is `Preserve` or `Reset`. Its optional `fitModeTransition` is `Preserve` or `SetExplicit`, where `SetExplicit` carries one valid `FitMode`. Its optional `spreadDirectionTransition` is `Preserve` or `SetExplicit`, where `SetExplicit` carries one valid `SpreadDirection`. Its optional `pageGapTransition` is `Preserve` or `SetExplicit`, where `SetExplicit` carries one finite non-negative real gap in logical spread units. Its optional `replacementIntent` is `NewTarget` or `SameTargetRefinement`; the latter is caller-supplied source or intent annotation that the replacement serves the same selected target, not source-identity inference by the viewport. The default policy is `RetainPrevious`, `Preserve` zoom, `Clamp` content position, `Preserve` rotation, `Preserve` mirror, `Preserve` fit mode, `Preserve` spread direction, `Preserve` page gap, and `NewTarget`.

For non-empty page-set replacement, the transition policy is applied atomically with page-set replacement. The caller supplies intent only; the viewport computes accepted page-set identity, retained-or-cleared visible display, fit/zoom/pan/rotation/mirror state, scan handoff, spread direction, page gap, spread geometry, and complete-spread commit from canonical viewport state. Clear-style page-set commands validate the same value type but otherwise follow the clear-style contract above. Invalid enum values, missing explicit fit mode, spread direction, or page gap for a `SetExplicit` transition, an explicit fit mode outside `Contain`, `FitWidth`, `FitHeight`, or `Manual`, an explicit spread direction outside `LeftToRight` or `RightToLeft`, a non-finite or negative explicit page gap, or `zoomTransition: ResetToContain` combined with `fitModeTransition: SetExplicit` to any mode other than `Contain` return `Invalid` without partial state application, provider work, retained-display changes, or request/display revision-token advancement.

`replacementIntent` never overrides explicit transition fields. `SameTargetRefinement` with `ClearBeforeLoad`, `SameTargetRefinement` with rotation or mirror reset, and `SameTargetRefinement` with explicit spread direction or page gap changes are valid combinations. Same-target refinement still creates a new accepted request for public revision and stale-result behavior; late results from the previous request cannot change the refined accepted request or visible display.

## Public Status

`RequestStatus` has the values `NoRequest`, `Loading`, `Ready`, `Unsupported`, and `Error`. `NoRequest` means no accepted page set is active, or no accepted sequence is active for a command-addressed role. `Loading` means an accepted request is waiting on metadata, request queueing, frame payload, preparation or upload ownership, positive item geometry becoming available, or render commit. `Ready` means the accepted request has committed display content; for a spread target this requires every role in the accepted page set to commit. `Unsupported` means the accepted request cannot be satisfied because the requested operation, capability, content, or payload shape is unsupported. `Error` means the accepted request failed because of malformed content or metadata, provider failure, provider protocol violation, invalid payload admission data, public-limit violation where documented, or render failure rather than a normal unsupported-content or unsupported-capability outcome.

`DisplayStatus` has the values `Empty`, `Ready`, and `Retained`. `Empty` means no display content is committed. `Ready` means the committed display identity belongs to the accepted request; a non-positive item size may still expose no presentable image area. `Retained` means committed display content belongs to an earlier request while the accepted request is loading, unsupported, or failed.

For a spread request, terminal `requestStatus`, `requestReason`, `errorString`, and warning ownership are projected from the required roles as one aggregate request. `Error` status takes precedence over `Unsupported`; when terminal status ties, the primary role's terminal reason and diagnostics take precedence over the secondary role's reason and diagnostics. If only one role has the winning terminal status, that role supplies the aggregate reason and diagnostics.

Accepted presentation readiness is `requestStatus == Ready`. Visible presentation readiness for inspection is `displayStatus == Ready || displayStatus == Retained`. Accepted-and-visible readiness is the combination `requestStatus == Ready && displayStatus == Ready`. A retained display may therefore be visible and inspectable while the accepted request is `Loading`, `Unsupported`, or `Error`; callers must not enable accepted-target actions from visible pixels alone. Commands operate on the accepted request/page set unless a method is explicitly documented as visible-presentation inspection, such as coordinate conversion over the retained displayed geometry.

`PlaybackPhase` has the values `Stopped`, `Playing`, `Waiting`, and `Paused`. `Stopped` means no playback driver is consuming sequence time. `Playing` means the active playback driver may advance when the addressed role's current frame and metadata allow it. `Waiting` means playback has been accepted for the active driver and is waiting for metadata to select a target, or has selected a target frame or position and is waiting for request queueing, provider work, preparation or upload ownership, positive item geometry becoming available, or render completion before consuming additional sequence time. `Paused` means the active playback driver preserves the current target without consuming sequence time.

`RequestReason` has the values `NoRequest`, `ProviderWaiting`, `RequestQueued`, `UploadPending`, `RenderWaiting`, `Ready`, `UnsupportedRequest`, `InvalidRequest`, `ProviderFailure`, `PayloadRejection`, and `RenderFailure`. `ProviderWaiting` means the accepted request is waiting for provider metadata or frame production, `RequestQueued` means the accepted display request has not entered its next provider, preparation, or render stage because a previously accepted operation in the same serialized pipeline must finish or release ownership first, `UploadPending` means a validated payload is waiting for preparation or upload ownership, and `RenderWaiting` means a prepared payload is waiting for positive item geometry or render commit acknowledgement. Once an older operation cannot affect public state, it is stale and must not keep the accepted request in `RequestQueued`; retained visible pixels alone do not imply `RequestQueued`. Request reasons describe the current accepted request only; command failures that publish diagnostics without replacing or changing the accepted request are reported through `commandReason`, while value-validation failures documented as preserving diagnostics report only through their command outcome. Supersession is an ordering event, not the current reason of the newly accepted request.

The valid status and reason pairs are: `NoRequest` with `NoRequest`; `Loading` with `ProviderWaiting`, `RequestQueued`, `UploadPending`, or `RenderWaiting`; `Ready` with `Ready`; `Unsupported` with `UnsupportedRequest`, `InvalidRequest`, or `PayloadRejection`; and `Error` with `ProviderFailure`, `PayloadRejection`, or `RenderFailure`. `PayloadRejection` pairs with `Unsupported` when the payload shape or size is outside the supported public contract, and with `Error` when metadata, payload envelopes, required validation data, provider protocol, or documented public-limit checks are malformed or invalid.

`CommandReason` has the values `NoCommand`, `IgnoredNoRequest`, `InvalidRequest`, and `UnsupportedRequest`. Accepted commands clear `commandReason` to `NoCommand` unless they synchronously return a more specific non-accepted outcome or are accepted `setSpreadDirection(...)` or `setPageGap(...)` no-ops with no observable value change. Except for invalid `setSpreadDirection(...)` and `setPageGap(...)` values documented below, invalid, unsupported, and ignored commands update `commandReason` and `commandRevision` without changing `requestStatus`, `requestReason`, accepted target, display status, retained display content, playback phase, or request revision.

Request, display, and command revisions are opaque monotonic revision tokens. Within an item lifetime, a newer public change receives a token that is distinct from earlier tokens and tokens never reset except by item destruction; the public contract does not require QML callers to compare numeric ordering. Stale rejection is viewport-owned and must not depend on JavaScript numeric precision or caller-maintained revision arithmetic. The request revision token changes when the accepted request identity, request status, request reason, requested target, metadata-derived public observations for the accepted generation, or public diagnostic for that request changes. The display revision token changes when visible display content, display ownership, display status, presentation-affecting geometry, background presentation, mirroring, fit mode, zoom percent, content position, pannability, spread direction, page gap, rotation, scan position, or an observable quality fallback changes, including presentation-only changes while `displayStatus` is `Empty`. The command revision token changes when the command diagnostic generation changes: except for invalid `setSpreadDirection(...)` and `setPageGap(...)` values documented below, every invalid, unsupported, or ignored command advances it even when the resulting `commandReason` value repeats, and an accepted command advances it only when it clears a previous non-`NoCommand` diagnostic to `NoCommand`. Property-specific notifications remain the stable observation path for callers that only need one field.

For `setSpreadDirection(...)` and `setPageGap(...)`, changing the canonical public value emits the matching property notification and advances `displayRevision`; `requestRevision` does not advance because the accepted request, playback phase, and caller-owned source selection are unchanged. Setting the current direction or current gap is an accepted no-op that does not emit a property notification, clear prior command diagnostics, or advance any revision. Invalid direction or gap input returns `Invalid` and preserves the previous value, geometry, display state, request state, provider work, playback phase, diagnostics, and all revision tokens.

## Public Value Types

Public range, rectangle, size, point, coordinate-result, page-geometry, page-set-transition-policy, command-outcome, and revision-token results are stable typed value types available to C++ callers and registered as QML value types. They are not `QVariantMap` contracts; callers can rely on named fields, units, invalid-value rules, equality behavior, and type-stable delivery across C++ and QML.

Public range values expose `minimum` and `maximum` integer fields in the units of the property that owns the range. An invalid range has `minimum: -1` and `maximum: -1`; otherwise both fields are inclusive bounds.

Public rectangle values expose real-valued `x`, `y`, `width`, and `height` fields in the coordinate space named by the property. Empty or unavailable rectangles use `width <= 0` or `height <= 0`; callers must not infer an image-space origin from an unavailable rectangle.

Public size values expose real-valued `width` and `height` fields. Public point values expose real-valued `x` and `y` fields. Public coordinate-result values expose `valid`, `x`, and `y` fields plus the coordinate space implied by the method that produced them; invalid coordinate results use `valid: false`, `x: 0`, and `y: 0`. Public page-geometry values expose the page role, page rectangle in spread coordinates, item rectangle, visible page rectangle, and availability state for that role.

Public revision-token values expose equality and invalid-token testing. If a build also exposes a numeric projection for diagnostics, it is advisory; stale-sensitive command acceptance and late-result rejection remain viewport-owned and are reported through command outcomes, request state, and typed token matching rather than QML numeric comparisons.

QML notifications are emitted when any field of a public value changes according to exact numeric equality for integer fields and exact equality of the normalized public value for real fields. C++ callers observe the same field names and units through the equivalent value types.

## Position Observations

The viewport's public timing model is integer milliseconds. Sequence factories and provider adapters supply or normalize timing metadata to integer millisecond frame boundaries before the viewport validates seek bounds, total duration, requested position, or displayed position. Providers may preserve higher-precision timing internally, but public viewport seeking and observation use the normalized millisecond intervals only.

`requestedPosition` is the accepted public target position in milliseconds when the accepted request was created from a position seek or playback advancement. For a timed frame-identity request, including frame seek, initial display, and metadata-bound selection, it is the start position of the selected frame when timing metadata is known and `-1` while no position identity is available. Still-image requests always expose `requestedPosition: -1`.

`requestedFrame` is the accepted public target frame index when a frame identity is known. A syntactically valid frame seek uses a non-negative frame index and publishes the requested zero-based frame index immediately, even while metadata bounds are unknown and the target still requires later revalidation. Initial display, metadata-bound selection, position seek, and playback advancement expose the selected or resolved zero-based frame index once metadata resolves the target. It remains `-1` while metadata has not resolved a frame identity, including playback accepted before metadata selects a target and unknown-target initial display before metadata-bound selection.

The public requested target is distinct from the resolved frame identity used for provider frame validation. A position seek preserves the caller's accepted public position, including positions inside a frame interval and `totalDuration`; the resolved frame identity is the selected frame index and that frame's start position after public timing normalization. For `seekToPosition(totalDuration)`, the valid resolved frame identity is the final frame index and final frame start position even though public `requestedPosition` remains `totalDuration`.

`displayedPosition` is the start position in milliseconds of the displayed frame's half-open interval. If a caller seeks exactly to `totalDuration`, `requestedPosition` remains `totalDuration`, the selected displayed frame is the final frame, and `displayedPosition` is the final frame's start position after commit. In play-once mode, the terminal displayed frame keeps its frame-start `displayedPosition`; playback stopping at the end does not expose an out-of-range displayed position. In looping mode, the first accepted request after wrap has `requestedPosition: 0` and later commits with `displayedPosition: 0`; no transient position greater than `totalDuration` is public.

Still-image sequences have one public frame and no public timing identity. They expose `frameCount: 1`, `frameSeekSupport: True`, `frameSeekBounds: 0..0`, `timedPlaybackSupport: False`, `positionSeekSupport: False`, `totalDuration: -1`, invalid position seek bounds, `requestedPosition: -1`, and `displayedPosition: -1`. `seek(0)` is accepted as an explicit display request for the still frame; other frame indices are invalid, and `seekToPosition(...)` and `play()` are unsupported.

## Authored Animation Facts

Timed sequences may carry authored animation facts in addition to generic playback capability. The public authored facts are autoplay eligibility for the accepted initial display, progressive animation readiness support, and authored loop policy. Authored loop policy distinguishes no authored loop, finite loop count, and infinite loop; a finite loop count is an integer count of authored playback iterations and is not equivalent to the caller's boolean `looping` override. When `looping` is `false`, authored loop policy controls playback end behavior; when `looping` is `true`, the caller override forces effective infinite looping for the active timed sequence.

Autoplay eligibility is caller/provider intent attached to the sequence facts. When an accepted initial display is autoplayable, the viewport accepts playback intent through the same request path as `play()` after the initial target is selected, reports `Waiting` until the initial target commits, and starts consuming sequence time only after the initial target commits as the accepted visible display. It does not expose a separate caller-owned timer or require QML to schedule frame changes. If the caller pauses, stops, seeks, replaces the page set, clears the viewport, or changes the looping override, the explicit caller command supersedes authored autoplay according to the normal playback and stale-result rules.

Progressive animation readiness means the first frame may commit before all later frames are available. Later frames still require accepted request ordering, payload validation, and render commit before they can become visible. Retained display rules are unchanged: previous pixels may remain visible only when the active transition selected retention, and retained pixels never make the accepted animation target ready.

## Unavailable Values

Unknown integer counts and frame indices are exposed as `-1`. Unknown durations and positions are exposed as `-1` milliseconds. Unknown seek bounds are exposed as an invalid range whose minimum and maximum are both `-1` milliseconds or frame indices, matching the unit of the seek mode.

Unknown booleans, including timed playback support, frame seek support, and position seek support before provider metadata is validated, are exposed through a tri-state value with `Unavailable`, `False`, and `True` states rather than by guessing.

Unavailable image sizes and rectangles are exposed as empty values with non-positive width or height. Non-positive item geometry makes presentable rectangles and coordinate conversions unavailable, but does not clear `displayedImageSize` while display content remains committed. Invalid coordinate conversions return `valid: false` coordinate-result values and must not be represented by clamping to an edge pixel.

## Command Outcomes

Command outcomes distinguish accepted, invalid, unsupported, and ignored because there is no active request for the addressed page set or role. A command outcome reports immediate command acceptance; asynchronous provider or render failure is reported through request status.

Command admission follows one public precedence order for calls that reach the viewport command boundary. Malformed enum values, invalid public value objects, missing required fields in command value types, invalid transition-policy shapes, and non-finite numeric arguments return `Invalid` before capability or failure-scope checks. After syntax and type validation, role-scoped commands addressed to a role that is not present in the accepted page set return `IgnoredNoRequest`. For a present role, intrinsic domain errors such as negative frame indices, negative positions, and targets outside known seek bounds return `Invalid` before unsupported-capability or generation-terminal checks. Unsupported capability and generation-terminal checks run only after the command input is otherwise valid for the addressed active role.

`clear()` always succeeds, stops playback, removes retained content, and moves request and display status to their empty states. Role-scoped `play()`, `pause()`, `stop()`, `seek(frame)`, and `seekToPosition(milliseconds)` commands addressed to a role that is not present in the accepted page set return `IgnoredNoRequest` and leave request, display, and playback state unchanged. The viewport has one active playback driver; accepting `play(role)` selects the addressed role as that driver and supersedes playback advancement for any previously playing role. `pause(role)` or `stop(role)` addressed to a present role that is not the active playback driver is accepted as a no-op for playback ownership: it does not stop or pause another role's active driver, does not change request/display state, and only clears prior command diagnostics according to normal accepted-command rules. `stop()` for the active playback driver exits playback without seeking and supersedes only pending requests created by playback advancement; it does not select a target other than the latest non-playback target for the generation and does not change display content by itself. If a non-playback request is still the active accepted request, `stop()` leaves it eligible to commit. If playback had superseded the latest non-playback target, `stop()` creates a fresh accepted non-playback display request identity for that same target, or promotes already committed same-generation content for that target to the accepted display identity; old provider, preparation, and render results for the previously superseded request identity remain stale. If playback was waiting on metadata after superseding an unknown-target initial request, `stop()` creates a fresh unknown-target non-playback initial request identity with unknown requested frame and position, and later validated metadata may create the metadata-bound initial frame `0` request from that fresh identity. If the generation has no latest non-playback target and no initial target pending metadata, requested frame and position remain unknown until metadata or an explicit command selects one. `pause()` for the active playback driver preserves the current requested target; it changes playback phase from `Playing` or `Waiting` to `Paused`, and otherwise succeeds for an active request without changing playback phase. `resetView()` sets `fitMode` to `Contain`, updates `zoomPercent` from the contain fit, resets the manual zoom demand to that default view, and moves content position and scan state to the scan-start position clamped to the current spread, spread direction, page gap, rotation, mirror state, and item geometry. With no presentable geometry, it stores the default view preference while geometry observations remain empty. It does not change the active page set, spread direction, page gap, rotation, mirroring, background, quality preferences, looping, or authored animation facts.

Presentation commands are accepted or rejected by the viewport against the current presentation state. `setSpreadDirection(direction)` accepts `LeftToRight` or `RightToLeft` as canonical spread placement state. `setPageGap(gap)` accepts finite non-negative logical spread units as canonical gap state. These standalone setters do not replace the accepted page set, change accepted request identity, start or cancel provider work, change playback ownership, or change source identity; they recompute spread placement, content size, pannability, visible rectangles, page rectangles, coordinate conversion, scan bounds, and clamped content position from canonical viewport state. `setFitMode(mode, anchor)` accepts valid fit modes, preserves the anchor when there is presentable geometry, and clamps content position when the resulting geometry cannot preserve it. `setZoomPercent(percent, anchor)` accepts valid manual zoom values, selects `Manual` fit mode, stores the canonical manual percent, preserves the anchor when there is presentable geometry, and clamps content position when the resulting geometry cannot preserve it. Quarter-turn rotation and mirror commands keep the anchor stable when possible and clamp content position when the resulting geometry cannot preserve it. Pan commands operate in viewport-owned content coordinates, `panToStart()` and `panToEnd()` use the current spread direction and rotation-aware scroll bounds, and scan commands advance the viewport-owned scan position over the visible spread bounds. Invalid presentation command parameters, such as non-finite anchors, non-finite zoom, non-positive zoom percent, zoom percent above the published manual-zoom limit, non-finite pan deltas, invalid fit modes, negative page gaps, non-finite page gaps, or invalid spread directions, return immediate command outcomes and must not require QML to repair canonical geometry state. Setting the current spread direction, setting the current page gap, setting a fit mode to the current mode, setting manual zoom to the current percent, setting a mirror axis to its current value, panning when there is no scrollable range, panning to the already-current boundary, and scanning past the first or last segment are accepted no-ops and do not change display revision unless another observable presentation value changes.

Command behavior after an unsupported or error request depends on the failure scope after the command admission precedence above has accepted the addressed active role and validated the command input. Generation-terminal unsupported or error requests cannot accept new display or playback requests until `clear()` or sequence replacement. Display-request-terminal unsupported or error requests keep the accepted generation usable; later valid explicit seeks, and playback-selected targets when playback is supported, are evaluated against the accepted generation's metadata and capabilities. For spread targets, terminal command and request outcomes are evaluated against the addressed role, while aggregate `requestStatus` and `requestReason` still describe the accepted target spread as a whole.

## Public Limits

The installed API exposes one limits object named `ImageSequenceLimits` as both a QML singleton and a C++ type with static read-only accessors using the same field names. It reports `maximumLogicalWidth`, `maximumLogicalHeight`, `maximumPixelsPerFrame`, `maximumPayloadBytesPerFrame`, `maximumTimedListFrameCount`, `maximumFrameDuration`, `maximumTotalSequenceDuration`, and `maximumDiagnosticStringLength`; duration fields use integer milliseconds, byte fields use bytes, pixel fields use logical pixels or pixel counts, and diagnostic length uses Unicode scalar values.

The installed API also exposes display-demand limits for viewport presentation, including `maximumManualZoomPercent`. `maximumManualZoomPercent` is finite, positive, and at least `100`; manual zoom commands above that published maximum return `Invalid` and leave fit mode, manual zoom, effective zoom, content position, and display revision unchanged. Source admission limits and display-demand limits are separate: a payload inside `ImageSequenceLimits` is not rejected merely because the caller asks for a large viewport or fit mode, and a manual zoom demand outside display limits is not converted into a payload rejection. If otherwise admitted content cannot be prepared or committed for the current presentation demand by the installed backend, the request reports `Error` with `RenderFailure` or a documented presentation quality fallback rather than silently lowering canonical zoom.

Concrete builds may publish higher `ImageSequenceLimits` values, but they must support at least 8192 logical pixels per frame side, 67108864 pixels per frame, 268435456 payload bytes per frame, 10000 timed-list frames, 86400000 milliseconds per frame, 86400000 milliseconds total duration, and 4096 Unicode scalar values per public diagnostic string. Published source limits are end-to-end admission limits for the installed build; a backend-specific failure below the published source limit is reported as render failure, not silently treated as unsupported input.

Factory helpers reject construction input outside the published limits with synchronous diagnostics. Provider-backed content outside the published limits reports a request status and reason for the affected request according to the failure source. Public admission failures are distinct from backend capacity or backend-specific failures: malformed metadata or payload envelopes, missing payload byte-size metadata when the viewport cannot derive a conservative byte size before retention or upload, metadata public-limit violations, frame payload size or byte-limit violations, and publicly unsupported payload shapes report `PayloadRejection`. Publicly unsupported payload shapes and frame payloads outside published frame size or byte limits use `Unsupported` with `PayloadRejection`; malformed metadata or payload envelopes, missing required byte-size metadata, metadata public-limit violations, and provider protocol violations use `Error` with `PayloadRejection`. Otherwise supported payloads at or below the published limits that fail because the installed rendering backend cannot prepare or commit them report `Error` with `RenderFailure`. Payload-rejection diagnostics are redacted and bounded, but may identify the broad admission category that failed.

| Condition | Request status | Request reason |
| --- | --- | --- |
| Metadata accurately describes unsupported sequence content | `Unsupported` | `UnsupportedRequest` |
| Metadata accurately describes an unsupported operation or capability for otherwise valid content | `Unsupported` | `UnsupportedRequest` for the active operation or display request only |

## Sequence Construction

`ImageSequence` is an opaque caller-facing handle for immutable or provider-backed image content. Callers create sequences through explicit helpers instead of assigning raw inputs to the viewport.

The construction concepts are a still image sequence, a timed frame list sequence, and a provider-backed sequence. QML-callable helpers accept only QML-representable helper objects; C++ helpers may accept native image values when appropriate. The stable QML construction helper signatures are `ImageSequenceFactory.fromFrame(frame: ImageFrame): ImageSequenceFactoryResult`, `ImageSequenceFactory.fromTimedFrameList(list: TimedImageFrameList): ImageSequenceFactoryResult`, and `ImageSequenceFactory.fromProvider(adapter: ImageSequenceProviderAdapter): ImageSequenceFactoryResult`; C++ exposes equivalent helpers with native overloads where appropriate. `ImageSequenceFactoryResult` exposes `sequence`, `outcome`, `errorString`, and `warningString`; failed construction returns `sequence: null` with a bounded diagnostic. `FactoryOutcome` values are `Created`, `Invalid`, `Unsupported`, and `Error`.

Invalid construction input fails at construction time with synchronous factory diagnostics. A valid provider-backed sequence may subsequently report unsupported or error status after assignment if provider startup or content requests fail.

Still-image and timed-list factories derive construction-time capability facts from their validated construction input. Provider-backed sequences derive construction-time capability facts from adapter declarations and cheap known metadata. Timed-list and provider-backed sequences may also declare authored animation facts: autoplay eligibility, progressive animation readiness support, and authored loop policy. Authored facts are represented by `ImageSequenceAuthoredAnimationFacts`, whose `LoopMode` is `PlayOnce`, `Finite`, or `Infinite`; `finiteLoop(count)` uses `count` as the total authored playback iterations and requires `count >= 1`, while `infiniteLoop()` represents authored infinite looping. `TimedImageFrameList` exposes `authoredAnimationFacts()` and `setAuthoredAnimationFacts(...)`, provider adapters expose construction-time `authoredAnimationFacts()`, and provider metadata may supply runtime `authoredAnimationFacts()` for the accepted generation. Those facts affect viewport playback behavior only after the sequence is accepted by a viewport and do not give the viewport ownership of source discovery, decoding, cache, or predecode policy.

Provider-backed sequence construction establishes sequence identity, provider ownership, declared provider capabilities, construction-time facts, authored animation facts, and a provider threading contract. Destroying the original adapter QObject after successful sequence construction does not invalidate already-created sequences or active sessions. If provider-owned external resources become unavailable after assignment, the active generation reports provider failure through the session; if the adapter cannot create a sequence that survives adapter QObject destruction under that contract, construction fails with factory diagnostics.

Provider-backed sequence construction starts each capability as one of `Unavailable`, `DeclaredFalse`, `DeclaredTrue`, or `KnownTrue`/`KnownFalse` from construction-time facts. These construction states are capability facts, not the public QML observation enum: `Unavailable` projects to public `Unavailable`, `DeclaredFalse` and `KnownFalse` project to public `False`, and `DeclaredTrue` and `KnownTrue` project to public `True`. Runtime metadata may resolve `Unavailable` to true or false. Runtime metadata that contradicts `DeclaredFalse`, `DeclaredTrue`, or construction-time facts is malformed metadata and maps to `Error` with `PayloadRejection`; it is not treated as a normal capability resolution.

Provider construction facts are represented by `ImageSequenceProviderKnownFacts`. The value can be unknown, logical-size-only, still, timed-frame-count, fixed-duration, or timed-frame-list. Unknown facts provide no metadata observations before runtime metadata. Logical-size-only facts constrain runtime metadata logical size but do not provide frame count, duration, seek bounds, or an initial display target. Timed-frame-count facts constrain runtime metadata frame count and may expose frame count and frame seek bounds when frame seeking is declared or known true, but they do not provide total duration or position bounds. Fixed-duration and timed-frame-list facts are complete timed facts. Still facts and complete timed facts are complete construction metadata and may select initial frame `0` at assignment time. The compatibility `knownMetadata()` adapter method is a supported public declaration path; valid complete `knownMetadata()` values project to equivalent known facts.

Frame count, total duration, frame durations, public logical image size, and seek bounds are unknown until provider metadata is validated unless the provider declares them as construction-time facts through the public adapter API. Construction-time facts are authoritative constraints for the accepted generation; runtime metadata that contradicts those facts is malformed metadata and maps to `Error` with `PayloadRejection`. Partial facts only project observations that are safe without complete runtime metadata: logical size constrains validation but does not select a target, frame count can project frame bounds only when frame seek support is known true, and total duration or position bounds project only when complete durations are known.

`ImageSequenceProviderThreadingContract` has the values `AffinityBound` and `ThreadSafe`. `ImageSequenceProviderAdapter::threadingContract()` defaults to `AffinityBound`. Affinity-bound sessions receive entry-point calls on the session QObject affinity. Thread-safe sessions may receive session entry-point calls directly from the viewport controller affinity, while session QObject destruction remains on the session affinity.

## Frames And Timed Lists

`ImageFrame` represents an immutable display-ready frame payload and its metadata. The public API does not expose mutable raw pixel storage as viewport state.

Frame logical width and height must be positive finite integers. Public logical image size is the orientation-normalized image size that callers observe through geometry, coordinate conversion, and displayed image size; physical payload dimensions may differ when the declared orientation rotates or otherwise transforms the payload into that public logical image space. A sequence has one public logical image size for every frame in that sequence; timed-list construction rejects entries whose public logical image size differs from the first accepted frame, and provider-backed frame payloads whose envelope public logical image size differs from validated sequence metadata report `Error` with `PayloadRejection`. Frame payload metadata must describe the public logical image size, transparency, and orientation that callers can observe through viewport geometry and presentation. Invalid frame metadata is rejected during factory construction or reported as payload rejection for provider-backed content.

`ImageFrame::OrientationPolicy` follows the eight Qt image I/O transformation states: `Identity`, `MirrorHorizontally`, `MirrorVertically`, `Rotate180`, `Rotate90`, `MirrorHorizontallyAndRotate90`, `MirrorVerticallyAndRotate90`, and `Rotate270`. `Rotate90`, `MirrorHorizontallyAndRotate90`, `MirrorVerticallyAndRotate90`, and `Rotate270` swap public logical width and height relative to the physical payload. A C++ `ImageFrame(QImage, OrientationPolicy, QObject*)` constructor creates a frame whose public logical size, geometry, coordinate conversion, and pixel content are already orientation-normalized for viewport callers.

`TimedImageFrameList` is a builder for explicit animated sequences. It owns typed frame-duration entries, exposes a count, supports append and clear operations, and reports construction diagnostics when invalid entries are rejected.

Timed lists use zero-based frame indices. Durations projected to QML use milliseconds and must be positive. Empty lists, zero-duration frames, negative durations, non-finite durations, and total durations that exceed published range limits are invalid construction input. Provider-origin timing may preserve fractional precision internally, but adapter metadata accepted by the viewport provides integer millisecond frame boundaries or durations; conversion to that public timing model is the provider adapter's responsibility.

## Provider Adapter

`ImageSequenceFactory.fromProvider(...)` or the equivalent C++ helper adapts an application-owned provider adapter into an `ImageSequence`. The provider object itself is not assigned directly to the viewport.

The public provider adapter surface is sufficient for downstream applications to implement custom sources without including private headers or touching scene graph objects. Detailed public session, threading, token, result, cancellation, payload, and failure semantics are specified by [ImageSequence Provider Adapter](image-sequence-provider-adapter.md).

Provider integration is a trusted in-process extension point. The public API guarantees bounded entry-point expectations, opaque session-scoped request tokens echoed on provider results, deterministic construction diagnostics, deterministic unsupported/error state mapping after assignment, and rejection of closed-generation tokens for later generations even if token values compare equal outside their session identity.

## Status And Diagnostics

Public enum values are scoped and stable enough for QML branching.

`errorString`, `warningString`, and factory diagnostic strings are user-presentable, redacted, bounded plain text. Public diagnostics do not expose provider private data, file-system paths, URLs, credentials, raw exception text, or unbounded payload excerpts unless the application explicitly supplied that same text as user-facing content.

`errorString` describes the current accepted display request for the accepted page set, using the aggregate spread-failure projection when multiple required roles are involved. `clear()`, a new accepted sequence assignment, and any accepted display-request identity change clear it before the new request reports its own terminal diagnostic, and transition to `Ready` clears any previous error for that request. Retained display content does not retain the previous generation's error string. Command-only failures that publish command diagnostics are reported through `commandReason` and do not change `errorString`; value-validation failures documented as preserving diagnostics do not change `errorString` or `commandReason`.

`warningString` is advisory. Callers may display or log it, but branchable behavior comes from status, reason, command outcome, revision tokens, and capability observations. Optional quality degradation may set a warning, but the absence of a warning does not guarantee that every presentation preference was satisfied exactly. Warnings belong to the accepted request or the current presentation fallback that caused them; request-owned warning changes advance the request revision token, and presentation-fallback warning changes advance the display revision token. `clear()`, a new accepted sequence assignment, any accepted display-request identity change for request-owned warnings, successful replacement of the warned request, or resolution of the presentation fallback clears the warning. Retained display content does not carry an earlier generation's warning into the accepted replacement.

## Out-Of-Scope API

The public API does not include implicit file or URL loading properties on `ImageViewport`, archive or directory navigation, active navigation scope, page number ownership, primary page selection, secondary page fallback policy, route transition meaning, shortcut availability, title selection, deletion target selection, archive navigation position, source identity ownership, decoder backend selection, cache backend selection, predecode backend selection, toolbar/action routing, built-in gesture controls, QML callback providers, numeric provider progress, scene graph resource injection, native texture payloads, tiled loading, region loading, render backend selection policy, or full color-management policy. Callers must not own or inject scene graph resources for viewport display; public API must not expose `QSGNode`, `QSGTexture`, `QRhi`, native texture handles, render-pass objects, or backend-specific resource lifetimes. As a `QQuickItem`, `ImageViewport` encapsulates scene graph and render-backend selection behind viewport properties, commands, revision tokens, and render acknowledgements. Out-of-scope concerns require explicit factories, adapters, application code, or presentation policies with their own contracts.
