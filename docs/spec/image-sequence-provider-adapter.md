# ImageSequence Provider Adapter

The provider adapter is the public extension point for application-owned image sources. It lets applications expose custom decoding, storage, or streaming services as an `ImageSequence` without giving `ImageViewport` direct access to files, URLs, archives, or arbitrary JavaScript objects.

## Public Contract

A downstream provider is implementable from installed public headers and linkable through the installed package target. It must not require private headers, internal controller types, source-tree include paths, or build-tree-only QML imports.

The adapter base is an abstract QObject-compatible type suitable for C++ implementations and QML ownership. It is not directly creatable as a complete provider from QML.

Factory construction adapts a concrete provider adapter into an `ImageSequence` using side-effect-free metadata and a bounded provider-session factory. Expensive probing, network access, archive access, decoder startup, or scene graph work begins only after a viewport accepts the sequence.

Construction-time provider data is limited to sequence identity, declared capabilities, cheap known facts, compatibility known metadata, a threading contract, and the ability to create a bounded session. Cheap known facts supplied at construction time are authoritative constraints for generations created from that sequence. Runtime metadata supplied by a session becomes authoritative only after the viewport validates it against the public limits, the construction-time constraints, and the active generation identity.

Construction-time work may read already-materialized adapter fields and create cheap value objects; it must not perform blocking filesystem inspection, cache population, decoder header probing, network calls, archive traversal, service calls, or scene graph work. A bounded provider-session factory is an object that can create an independent session with bounded local bookkeeping and without starting expensive source work until the viewport accepts the sequence and opens the session.

Constructed sequences and active sessions remain deterministic after the original adapter QObject goes out of scope. Adapter QObject destruction is not itself a provider failure. If the provider cannot create sessions that survive under that public lifetime contract, sequence construction fails with factory diagnostics rather than creating a sequence that can later dangle.

## Public Session API

Adapting a provider creates a provider-backed sequence. Assigning that sequence to a viewport first registers the viewport request generation, then opens a public provider session for that generation. If session opening fails after assignment, the generation remains observable and reports provider failure. Sessions are independent; concurrent viewports or replacements must not require shared mutable request state unless the provider explicitly owns that sharing.

The session command surface distinguishes metadata requests, non-playback frame display requests, non-playback position display requests, playback-advancement requests, cancellation, and close. Known-target initial display requires complete validated construction-time facts for the selected timing model and uses the non-playback frame display request entry point with frame `0` and a token. Metadata-bound target selection after an unknown-target initial assignment also uses the non-playback frame display request entry point. Explicit caller `seek(frame)` uses the non-playback frame display request entry point. Explicit caller `seekToPosition(milliseconds)` uses the non-playback position display request entry point after the viewport resolves the frame identity from metadata; the provider receives the resolved frame index and the public requested position. `seekToPosition(totalDuration)` receives the final frame index and requested position equal to total duration, not end of sequence. Unknown-target initial assignment requests metadata first and sends no frame or position request until metadata-bound target selection. Playback advancement uses a separate session-scoped playback token that is not a public display-request identity; a playback token may return frame readiness for a resolved playback target or end of sequence for playback policy handling. Providers must not infer caller explicitness from the non-playback frame display request entry point. Each metadata, frame, position, or playback request carries an opaque public request token generated by the viewport-facing API. Providers echo the token on every result and do not infer ordering from pointer identity, callback order, or object lifetime. Tokens are scoped to the provider session and remain unique within that session for as long as late results can arrive.

The public session API includes `requestPosition(token, resolvedFrame, requestedPosition)`. Its base implementation delegates to `requestFrame(token, resolvedFrame)` so providers that only override `requestFrame` remain source-compatible and receive position display requests as frame requests. Providers that need to distinguish caller position seeks override `requestPosition`.

Session entry points are called according to the provider adapter threading contract. `AffinityBound` is the default and calls session entry points on the session's QObject affinity. `ThreadSafe` permits the viewport controller to call session entry points directly from its own affinity even when that differs from the session QObject affinity. QObject destruction still occurs on the session affinity for both contracts. Result delivery into the viewport is queued through the adapter API; providers must not synchronously call back into viewport commands from a session entry point.

The public result channel distinguishes metadata ready, frame ready, waiting or progress, end of sequence, unsupported request, cancelled request, and provider failure. Every terminal result includes the request token it terminates and optional public diagnostics. Unsupported results also carry an unsupported cause: unsupported operation for requests or capabilities the provider cannot perform, or unsupported payload for supplied content shapes the viewport should reject as payload admission. Waiting or progress results are advisory and may be coalesced by the viewport. The viewport does not expose numeric progress as public state; applications that need source-specific progress should expose it through their own provider-facing UI and treat viewport progress results as request-state hints only.

Terminal provider results map to public viewport state deterministically. `Frame ready` is terminal for the provider frame request it answers, but it moves the viewport request to ready only after payload validation and render commit. `End of sequence` is valid only as a provider-session result for playback advancement beyond the final displayable interval; it is not a public display request and must not expose a beyond-final requested target. Explicit `seekToPosition(totalDuration)` resolves to the final frame and must not be answered with end of sequence. In play-once playback, end of sequence selects or promotes the final displayable frame; playback stops only after that frame is already committed for the accepted request or same-generation final-frame pixels are promoted to the accepted display identity, and if the final frame is not current for the same generation, the final frame remains the active display request. In looping playback, end of sequence requests the first frame without exposing an out-of-range position. `Unsupported request` with unsupported-operation cause reports `Unsupported` with `UnsupportedRequest`; unsupported-payload cause reports `Unsupported` with `PayloadRejection`. The legacy unsupported signal without a cause remains source-compatible: metadata-token results default to unsupported operation and frame or playback-token results default to unsupported payload. `Cancelled request` is terminal only for provider work and does not change public status when cancellation came from clear, replacement, close, or supersession. A provider-originated cancellation for a still-active token that the viewport did not cancel reports `Error` with `ProviderFailure` because the provider did not produce the accepted request. `Provider failure` reports `Error` with `ProviderFailure`.

Provider-session cancellation and close are best-effort adapter commands visible to provider implementers, not caller-facing `ImageViewport` commands. A cancelled request may still complete later, but its late results are ignored if the viewport has already accepted a newer request or closed the session. Closing a session releases viewport interest in all outstanding request tokens and prevents later provider output from changing viewport state.

Frame-ready results transfer a payload handle plus cheap envelope metadata: public logical image size, frame index, frame-start position for timed sequences, frame duration when known, transparency, orientation policy, payload byte size or a conservative byte-size upper bound when the viewport cannot derive one before retention or upload, and any format identifier needed by the installed public API. The public logical image size is the orientation-normalized image size that callers observe through viewport geometry, coordinate conversion, and `displayedImageSize`. The viewport normalizes payload pixels according to the frame orientation policy before render admission, display geometry, and payload-size comparisons that depend on public logical dimensions. Ownership transfer is explicit; if the viewport rejects or drops a payload, the payload handle is released exactly once through the public ownership contract and without requiring scene graph access from the provider.

## Provider Responsibilities

Provider entry points return after bounded local bookkeeping and report asynchronous progress through the result channel defined by the public adapter API. Providers must not require the viewport to block the GUI thread for decoding, I/O, network access, archive access, or service calls.

Provider results identify the logical request they answer and distinguish sequence metadata, frame readiness, waiting/progress, end of sequence, unsupported requests, cancellation, and provider failure.

Metadata-ready results are complete for the selected timing model. They provide the generation facts needed for validation and public observations: timing model, frame count, sequence-wide public logical image size, frame seek support, position seek support, timed playback support, and the seek bounds and timing data required by that timing model. If a provider cannot provide those mandatory facts yet, it reports waiting or progress instead of metadata ready; if it cannot provide them at all, it reports unsupported or provider failure according to the cause. Timing models are either still, fixed-duration frame sequence, or explicit variable-duration frame intervals. A still timing model exposes one indexed frame, frame seek support `True`, frame seek bounds `0..0`, no public duration, position seek support `False`, and timed playback support `False`. Timed frame intervals are half-open integer millisecond intervals, start at zero, are contiguous, have positive duration, and derive total duration from the exclusive end of the final interval. Position seek bounds are inclusive from zero through total duration, with `seekToPosition(totalDuration)` selecting the final frame. Until metadata is ready, callers observe unknown metadata values and loading request status except where construction-time facts safely provide specific observations.

Provider metadata failure classification is normative: unsupported sequence content reported by accurate metadata maps to generation-terminal `Unsupported` with `UnsupportedRequest`; unsupported operations or capabilities for otherwise valid sequence content map to `Unsupported` with `UnsupportedRequest` only for the active operation or display request that required the capability; malformed metadata, non-contiguous timing, non-positive durations, invalid dimensions, construction-time contradiction, protocol violation, or public-limit violation map to generation-terminal `Error` with `PayloadRejection`; metadata production failure after assignment maps to generation-terminal `Error` with `ProviderFailure`.

Frame-ready results provide enough cheap metadata for the viewport to validate dimensions, timing, byte-size limits, resolved frame identity, and payload admission before retaining or uploading the frame payload. The frame envelope public logical image size must match validated sequence metadata, and the frame index plus frame-start position for timed sequences must match the accepted display request's resolved frame identity after public timing normalization. The resolved frame identity is distinct from public `requestedPosition`; for `seekToPosition(totalDuration)`, a provider returns the final frame index and final frame start position. A resolved-frame-identity mismatch is a malformed payload envelope for that display request and reports `Error` with `PayloadRejection` when the generation metadata remains valid. If a provider omits byte-size metadata for a payload whose size the viewport cannot conservatively derive before retention or upload, the payload envelope is malformed and reports `Error` with `PayloadRejection`. Provider frame payload-rejection diagnostics identify the broad admission category, such as logical-size mismatch, byte-size metadata violation, resolved-frame mismatch, timing mismatch, or malformed frame metadata, while remaining redacted and bounded.

Cancellation and close requests are advisory but observable. Providers may finish local cleanup asynchronously, and late results for cancelled or closed requests are ignored by the viewport. Clear, replacement, item destruction, or terminal provider failure must not be blocked by provider cleanup.

Providers should coalesce or bound progress reports when production is faster than viewport consumption. The viewport may drop superseded progress reports, but it must preserve terminal results for the active request unless a newer request supersedes them.

## Failure Semantics

Failures detectable during factory construction, including an adapter's inability to provide a bounded session factory, should make sequence construction fail with factory diagnostics.

Failures detected after sequence assignment should leave the accepted sequence observable until the caller clears or replaces it, while request status reports unsupported or error state according to the failure. Adapter QObject destruction after construction is not a detected provider failure; provider-owned external resource invalidation after assignment reports provider failure for the active generation.

Provider protocol violations do not expose private provider details through public strings. Public diagnostics are redacted and stable enough for user presentation.
