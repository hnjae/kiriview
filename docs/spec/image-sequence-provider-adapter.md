# ImageSequence Provider Adapter

The provider adapter is the public extension point for application-owned image sources. It lets applications expose custom decoding, storage, cache, predecode, refinement, or streaming services as an `ImageSequence` without giving `ImageViewport` direct access to files, URLs, provider URLs, image-provider ids, archives, arbitrary JavaScript objects, display-store entries, or application navigation policy.

Provider-backed sequences are individual page sources from the viewport's perspective. The provider receives viewport requests and supplies provider events, diagnostics, declared facts, and complete-frame payloads for viewport demand; it does not own caller navigation policy, spread pairing, page-role selection, source identity comparison by the viewport, presentation-target transition intent, viewport presentation state, scene graph resources, or QML image load acknowledgement.

## Construction Contract

A downstream provider is implementable from installed public headers and linkable through the installed package target. It must not require private headers, internal controller types, source-tree include paths, or build-tree-only QML imports.

`ImageSequenceProviderAdapter` is an abstract QObject-compatible type. It exposes one construction method, `descriptor()`, returning `ImageSequenceProviderDescriptor`. The descriptor contains declared capabilities, cheap known facts, authored animation facts, threading contract, and a bounded session factory. Construction-time data is side-effect-free and authoritative for generations created from the sequence.

Construction-time and runtime metadata describe the source logical frame space, not necessarily the raster dimensions of every payload that will be returned later. Source logical size is stable geometry input for fit, zoom, pan, spread placement, coordinate conversion, and 100% zoom. Payload raster size is per-frame delivery metadata and may differ from source logical size for preview, first-display, bounded-detail, resolution-independent, or refinement workflows. The canonical demand and payload envelope schemas are defined in [ImageSequence Provider Protocol](image-sequence-provider-protocol.md#provider-demand-and-payload-values).

Factory construction adapts a provider descriptor into an opaque `ImageSequence`. Expensive probing, network access, archive access, decoder startup, cache population, or scene graph work begins only after a viewport accepts the sequence and opens a session.

Constructed sequences and active sessions remain deterministic after the original adapter QObject goes out of scope. If a provider cannot create sessions that survive under that lifetime contract, construction fails with factory diagnostics.

## Session Requests

`ImageSequenceProviderSession` has one request entry point: `request(const ImageSequenceProviderRequest&)`. Request values, request kinds, token fields, and display-demand fields follow the canonical schema in [ImageSequence Provider Protocol](image-sequence-provider-protocol.md).

Metadata requests ask for generation metadata. Frame requests ask for a resolved frame. Position requests preserve the public requested position and include the metadata-resolved frame identity needed for payload validation. Playback requests use a playback token and may return frame readiness or end-of-sequence. Frame, position, and playback requests carry `ImageSequenceProviderDisplayDemand`. Cancel and close requests are best-effort provider lifecycle requests; engine-side generation retirement happens before close delivery and does not depend on a close acknowledgement.

Display demand is advisory input for payload selection and mandatory input for stale-result validation. A provider may choose exact detail, first-display detail, bounded detail, cached detail, or a previous complete-frame payload that remains valid for the requested logical frame. Ignoring or degrading demand is allowed only when the returned payload still satisfies the active exactness preference; `RequireExact` rejects inexact payloads. Cached payload reuse must be reported under the current request token and current demand revision. Returning a payload whose envelope contradicts validated metadata, requested frame identity, public limits, active exactness preference, or active demand revision is not allowed.

Every metadata, frame, position, or playback request carries an opaque token generated by the viewport-facing API. Providers echo request tokens according to the protocol and do not infer ordering from pointer identity, callback order, or object lifetime. Tokens are scoped to the provider session and remain unique within that session while late events can arrive.

Session entry points are called according to the descriptor threading contract. `AffinityBound` calls entry points on the session QObject affinity. `ThreadSafe` permits the viewport-owned command-processing affinity to call entry points directly. QObject destruction still occurs on the session affinity for both contracts.

## Provider Events

The session reports one signal: `providerEvent(const ImageSequenceProviderEvent&)`. Event values, event kinds, unsupported causes, token echo rules, and diagnostic fields follow the canonical schema in [ImageSequence Provider Protocol](image-sequence-provider-protocol.md).

Terminal events include optional public diagnostics. Waiting and progress are advisory; the viewport may coalesce or drop stale progress events.

Frame-ready events transfer ownership with `ImageSequenceProviderFrameHandle` plus `ImageSequenceProviderFrameEnvelope`. Borrowed raw `ImageFrame*` result signals are not supported. Handle release is the provider-visible lifetime boundary for accepted, retained, rejected, stale, failed, cleared, replaced, memory-pressure-released, or item-destruction-released payloads. Release callback affinity, non-reentrancy, and session-destruction ordering follow the canonical handle contract in [ImageSequence Provider Protocol](image-sequence-provider-protocol.md#provider-demand-and-payload-values).

Primary and secondary page-role sessions use the same request and event channel. Role selection changes viewport aggregation and page placement; it does not restrict which provider event kinds are valid.

## Metadata And Payload Semantics

Metadata-ready events are complete for the selected timing model. They provide frame count, sequence-wide source logical size, frame seek support, position seek support, timed playback support, seek bounds, timing data, and authored animation facts when available.

A still timing model exposes one indexed frame, frame seek support true, frame seek bounds `0..0`, no public duration, position seek support false, and timed playback support false. Timed frame intervals are half-open integer millisecond intervals, start at zero, are contiguous, have positive duration, and derive total duration from the exclusive end of the final interval.

Frame-ready events must match validated sequence metadata and the active demand revision. The frame envelope source logical size must match sequence metadata, and frame index plus frame-start position for timed sequences must match the accepted request's resolved frame identity. Payload raster size may differ from source logical size, but the envelope must describe a finite positive complete-frame mapping whose aspect is compatible with the source logical frame after orientation normalization. `seekToPosition(totalDuration)` resolves to the final frame index and final frame start position; it is not an end-of-sequence event.

Provider metadata failure classification is deterministic. Unsupported sequence content maps to generation-terminal unsupported request state. Unsupported operations or capabilities for otherwise valid content map only to the active operation that required the capability. Malformed metadata, construction-time contradiction, protocol violation, or public-limit violation maps to generation-terminal error with payload rejection. Metadata production failure maps to generation-terminal error with provider failure.

Frame production failure maps to display-request-terminal provider failure. Unsupported payload maps to unsupported payload rejection. Malformed frame envelopes, missing required byte-size data, invalid payload raster size, invalid source-to-payload mapping, resolved-frame mismatch, timing mismatch, source-logical-size mismatch, and provider protocol violations map to error with payload rejection for the active display request.

Cancellation and close are advisory. A cancelled request may still complete later, but late events are ignored if the viewport has already accepted a newer request or closed the session. Clear, replacement, item destruction, or terminal provider failure must not be blocked by provider cleanup.
